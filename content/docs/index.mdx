This site is a public hub for SailPoint's API style and design guidelines—built to help teams ship
consistent, secure, evolvable APIs for customers and partners.

## Start here

If you're new, begin with this page, then choose a path:

- **Designing a new API**: read the core [Principles](/docs/principles), then work through the Rules
  categories as you model resources, errors, pagination, and security.
- **Reviewing an API**: use the Rules as a checklist (each rule has a stable ID you can cite in review
  comments and docs).
- **Implementing an API**: follow the Rules for the normative requirements; use the Reference section
  for checklists and recipes.
- **Integrating with SailPoint APIs**: use the Rules as a contract checklist for practical patterns
  (pagination, errors, retries) and terminology.

## Reading this documentation

### Normative language (RFC 2119)

These guidelines use RFC 2119 keywords:

- **MUST**: required for compliance.
- **SHOULD**: strongly recommended; exceptions must be justified and documented.
- **MAY**: optional; use when it improves client experience or operational safety.

### Rule IDs and stable references

Each rule heading includes a stable numeric ID, e.g. `[#401]`. Rule IDs exist so you can:

- Reference rules in reviews and design docs ("violates [#404]").
- Deep-link to a specific requirement.
- Automate checks (linters) against durable anchors.

## Recommended workflow

### For external readers (integrators)

- Treat the Rules as a **public checklist**: URL design, error handling, pagination, auth.
- Include **the rule ID** in feedback ("this violates [#404]") and link to the relevant rule section.

### For internal teams (designers/implementers/reviewers)

1. **Start with a resource model** — identify primary resources, identifiers, and relationships.
2. **Write the OpenAPI contract first** — keep OpenAPI as the single source of truth for contract + docs.
3. **Run a structured review** — review against the Rules category-by-category (URLs, payloads, errors, pagination, security).
4. **Implement and validate** — ensure runtime behavior matches OpenAPI examples and descriptions.
5. **Publish and maintain** — document non-obvious decisions; include compatibility notes for changes.

See: [Review checklist](/docs/appendices/review-checklist)
