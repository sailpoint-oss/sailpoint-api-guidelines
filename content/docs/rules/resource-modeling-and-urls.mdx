---
title: "Resource Modeling & URLs"
description: Rules for resource naming, URL structure, identifiers, and modeling API concepts cleanly.
---

These rules explain how to choose resource boundaries and URLs that stay understandable as the API grows.

Use this section to answer:

- Is this concept a resource, a workflow resource, or just an action?
- Should this relationship be nested or represented with filters?
- Will this URL still make sense to an external consumer a year from now?

---

## Resource & URL Design
### do-not-use-api-base-path
<RuleHeader
  id="do-not-use-api-base-path"
  level="MUST"
  title="Do Not Use /api Base Path"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET https://example.sailpoint.com/v2026/accounts`,
    },
  ]}
/>

- APIs MUST NOT include redundant base path segments like `/api` in public-facing URL paths.
- Configure environment-specific base URLs via OpenAPI `servers` and keep paths focused on domain-driven resource names (see [#use-domain-specific-resource-names]).

- ✅ `https://example.sailpoint.com/v2026/accounts`
- ❌ `https://example.sailpoint.com/api/v2026/accounts`

### define-canonical-url-forms
<RuleHeader
  id="define-canonical-url-forms"
  level="MUST"
  title="Define Canonical URL Forms"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/123`,
    },
  ]}
/>

APIs MUST define and enforce a canonical URL form:

- No duplicate slashes (`//`) or empty path segments.
- Define a trailing-slash policy and apply it consistently — prefer omitting the trailing slash.
- Use lowercase hyphenated path segments (see [#use-lowercase-hyphenated-path-segments-and-camelcase-path-parameters]).
- Avoid redundant base path segments like `/api` in public URLs (see [#do-not-use-api-base-path]).

- ✅ `/accounts/123`
- ✅ `/accounts/123/entitlements`
- ✅ `/identity-profiles/{identityProfileId}`
- ❌ `//accounts//123//`
- ❌ `/accounts/123/` (if trailing slashes are not canonical)
- ❌ `/accounts//123`
- ❌ `/Accounts/123` (wrong casing)

#### Server behavior

If a non-canonical form is received, either normalize internally, redirect to the canonical form, or reject with `400`.

### use-resource-oriented-urls
<span id="model-resources-avoid-action-endpoints" className="scroll-mt-28 block" aria-hidden="true" />
<span id="keep-urls-verb-free" className="scroll-mt-28 block" aria-hidden="true" />
<RuleHeader
  id="use-resource-oriented-urls"
  level="SHOULD"
  title="Use Resource-Oriented URLs"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `POST /accounts
PATCH /accounts/{accountId}
DELETE /accounts/{accountId}`,
    },
  ]}
/>

- URLs SHOULD use **noun-based paths**. Let HTTP methods express the action.
- SHOULD prefer resource-oriented endpoints over RPC/action-style endpoints. Model operations as HTTP verbs applied to resources.
- When a capability does not map to a standard CRUD verb, create a noun-like **request/job resource** rather than embedding a verb in the path.

- ✅ `POST /accounts` (create)
- ✅ `PATCH /accounts/{accountId}` (update)
- ✅ `DELETE /accounts/{accountId}`
- ✅ `POST /accounts/{accountId}/disable-requests` (request resource for a non-CRUD action)
- ✅ `POST /access-requests` (workflow resource)
- ❌ `POST /accounts/{accountId}/update`
- ❌ `GET /accounts/{accountId}/delete`
- ❌ `GET /accounts/{accountId}/disable`

### model-business-processes
<RuleHeader
  id="model-business-processes"
  level="SHOULD"
  title="Model Business Processes"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `POST /access-requests
GET /access-requests/{id}`,
    },
  ]}
/>

- APIs SHOULD model complete business processes and workflows as first-class resources, not just individual data entities.
- Prefer stable workflow resources that can be created, queried, and audited over ad-hoc action endpoints.
- Document the workflow in a step-by-step guide (see [#provide-an-api-user-manual]).

- ✅ `POST /access-requests` (create request)
- ✅ `GET /access-requests/{id}` (check status)
- ✅ `GET /access-requests?filters=...` (list)
- ✅ `POST /imports` (create import job)
- ✅ `GET /imports/{id}` (status/results)

### define-useful-resources
<RuleHeader
  id="define-useful-resources"
  level="SHOULD"
  title="Define Useful Resources"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/{id}?fields=(id,name,status)`,
    },
  ]}
/>

Resources SHOULD be designed around common workflows and support efficient retrieval:

- Resource boundaries SHOULD reflect domain concepts (see [#use-domain-specific-resource-names]).
- Primary workflows SHOULD be supported end-to-end (see [#model-business-processes]).
- Collections SHOULD support pagination (see [#support-offset-pagination-for-list-endpoints]) and conventional query params (see [#use-conventional-query-parameters]).
- Filtering and sorting SHOULD be available where lists would otherwise be unusable.
- Responses SHOULD be lean by default, with optional field selection or embedding when needed (see [#support-partial-responses-fields], [#allow-optional-embedding]).
- Field projection (`fields`, sparse fieldsets, or your API's equivalent) SHOULD be available on **collection GET** endpoints when clients routinely need slimmer payloads—not only on dedicated `POST /.../search` endpoints. If projection is limited to search for historical reasons, document that explicitly and plan to widen it where it reduces payload size without harming cacheability.

- ✅ `GET /accounts?filters=status eq "ACTIVE"&sorters=name:asc&limit=50&offset=0`
- ✅ `GET /accounts/{id}?fields=(id,name,status)`

Avoid exposing many near-duplicate resources or designs that require extra round-trips for the common case.

### use-domain-specific-resource-names
<RuleHeader
  id="use-domain-specific-resource-names"
  level="MUST"
  title="Use Domain-Specific Resource Names"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/standard_fields", label: "Google API Standard Fields" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts
GET /entitlements
GET /identity-profiles`,
    },
  ]}
/>

- Resource names MUST reflect domain concepts and business terminology, not technical implementation details (database table prefixes, internal service names, storage-layer jargon).

- ✅ `/accounts`, `/entitlements`, `/identity-profiles`
- ❌ `/dbUsers`, `/tblEntitlements`, `/internalAccounts`

### nest-sub-resources-only-when-tightly-coupled
<RuleHeader
  id="nest-sub-resources-only-when-tightly-coupled"
  level="MUST"
  title="Nest Sub-resources Only When Tightly Coupled"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `GET /users/{userId}/preferences`,
    },
  ]}
/>

Sub-resources MUST only be nested under a parent when they are tightly coupled — meaning:

- The sub-resource has no meaning without the parent (lifecycle is owned by the parent).
- Authorization is scoped to the parent.
- Its identity is only unique within the parent.

- ✅ `/users/{userId}/preferences`
- ✅ `/accounts/{accountId}/entitlements` (if entitlements are scoped to the account context)
- ✅ `/identity-profiles/{identityProfileId}/attribute-mappings`
- ❌ `/accounts/{accountId}/access-requests/{accessRequestId}` if access requests have a global ID and independent lifecycle — prefer `/access-requests/{accessRequestId}` with filters

### prefer-non-nested-urls-for-independent-resources
<RuleHeader
  id="prefer-non-nested-urls-for-independent-resources"
  level="SHOULD"
  title="Prefer Non-nested URLs for Independent Resources"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `GET /access-requests/{accessRequestId}`,
    },
  ]}
/>

- SHOULD prefer flat (non-nested) URLs when a resource has a globally unique ID, can exist without a single parent, and has its own lifecycle.

- ✅ `/access-requests/{accessRequestId}` (global workflow resource)
- ✅ `/entitlements/{entitlementId}` (if entitlements exist globally)
- ✅ `/accounts?identityId=...` (filter instead of nesting)

#### Alternatives to deep nesting

- Filter on a parent ID: `GET /entitlements?accountId={accountId}`
- Use a relationship resource: `GET /account-entitlements?accountId=...`
- Include links in payloads: `{ "links": { "entitlements": "/entitlements?accountId=..." } }`

### limit-resource-types
<RuleHeader id="limit-resource-types" level="SHOULD" title="Limit Resource Types" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

- SHOULD keep the number of distinct resource types manageable.
- Use query parameters, field filtering (`fields`), or embedding (`embed`) to support different views of the same resource rather than creating new resource types.
- Watch for warning signs: resources that differ only by a flag, multiple resources representing the same concept under different names, or clients needing many endpoints for a single workflow.

### limit-nesting-depth
<RuleHeader
  id="limit-nesting-depth"
  level="SHOULD"
  title="Limit Nesting Depth"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/{accountId}/entitlements`,
    },
  ]}
/>

- URL path nesting depth SHOULD be limited to 3 levels or fewer.
- If you need a fourth level, flatten the deeper resource into a top-level collection with filters.

- ✅ `/accounts/{accountId}/entitlements`
- ✅ `/identity-profiles/{identityProfileId}/attribute-mappings`
- ❌ `/orgs/{orgId}/identities/{identityId}/accounts/{accountId}/entitlements`

### use-rest-maturity-level-2
<RuleHeader id="use-rest-maturity-level-2" level="MUST" title="Use REST Maturity Level 2" externalDocs={[{ href: "https://martinfowler.com/articles/richardsonMaturityModel.html", label: "Richardson Maturity Model" }]} />

APIs MUST target at least **Richardson Maturity Model (RMM) Level 2**. In Fowler's model, Level 0 is RPC-on-HTTP; Level 1 introduces distinct resources but not necessarily full HTTP semantics; **Level 2** means you identify resources with URLs, apply the correct HTTP methods to them, and use HTTP status codes for outcomes. **Level 3** adds hypermedia-driven state transitions; SailPoint APIs do **not** require Level 3 (no mandate for HAL, JSON:API links, or other HATEOAS styles).

What you must change in practice:

- Use resource URLs (nouns), not action/RPC endpoints.
- Use HTTP methods correctly (see [#use-http-methods-correctly]) and respect method properties (see [#honor-method-properties]).
- Use standard, semantically correct status codes (see [#use-standard-http-status-codes]).
- Use standard content negotiation and media types (see [#use-standard-media-types]).
- Use a standardized error contract (Problem Details) (see [#define-a-standard-error-contract-in-openapi-problem-details]).

Hypermedia controls (RMM Level 3) are not required. Do not mandate HAL or JSON:API link schemas.

## Resource Identifiers
### use-url-friendly-ids
<RuleHeader
  id="use-url-friendly-ids"
  level="MUST"
  title="Use URL-Friendly IDs"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b`,
    },
  ]}
/>

- Resource identifiers used in URL path segments MUST be URL-friendly.
- Prefer opaque string IDs such as UUIDs (see [#define-numeric-formats]) or base64url-encoded identifiers.
- IDs MUST NOT contain spaces, characters requiring frequent percent-encoding, unescaped unicode, or `/`.
- Recommended safe character set for path segments: `[A-Za-z0-9._:-]` (and optionally `~`).

- ✅ `2c9180837c0a1234017c0a9999990000`
- ✅ `3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b` (UUID)
- ✅ `SGVsbG9fV29ybGQtMTIz` (base64url)
- ❌ `john doe` (space)
- ❌ `部门-1` (unicode)
- ❌ `a/b` (slashes break routing)

If an ID can include unsafe characters (e.g., legacy or natural keys), it MUST be carried as a query parameter or body field instead of a path segment.

### never-include-customer-org-names-in-paths
<RuleHeader
  id="never-include-customer-org-names-in-paths"
  level="MUST"
  title="Never Include Customer Org Names in Paths"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts`,
    },
  ]}
/>

- Public APIs MUST NOT embed customer org names or tenant identifiers in URL path structures.
- Determine tenant/org scope from the authentication context (token claims) and/or standard headers.

- ✅ `GET /accounts` (scope inferred from auth context)
- ❌ `GET /customers/acme-corp/accounts`
- ❌ `GET /orgs/{orgName}/accounts`

Internal-only administrative APIs may have different constraints; this rule applies to public, customer-facing APIs.

**Related rules**: [#secure-endpoints-with-oauth-2-0], [#enforce-tenant-data-isolation-in-responses]

### do-not-use-sequential-numeric-ids
<RuleHeader
  id="do-not-use-sequential-numeric-ids"
  level="MUST"
  title="Do Not Use Sequential Numeric IDs"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b`,
    },
  ]}
/>

Sequential IDs enable enumeration attacks and leak business scale.

- APIs MUST NOT expose sequential numeric identifiers as public resource IDs.
- Prefer UUIDs, ULIDs, or other opaque string identifiers.
- Non-sequential natural keys are acceptable only when truly stable and non-sensitive.
- Internal database surrogate keys may be sequential — just don't expose them directly.

### define-soft-delete-behavior
<RuleHeader
  id="define-soft-delete-behavior"
  level="SHOULD"
  title="Define Soft Delete Behavior"
  externalDocs={[{ href: "https://google.aip.dev/164", label: "Google AIP-164: Soft Delete" }, { href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `DELETE /accounts/123`,
    },
  ]}
/>

APIs that use soft delete SHOULD document and standardize the behavior so clients know exactly what `DELETE` means.

#### What DELETE returns

- Soft delete SHOULD return `200 OK` with the updated resource (including `deletedAt` timestamp) or `204 No Content`.
- Be consistent across the API.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": "123",
  "name": "Example Account",
  "status": "DELETED",
  "deletedAt": "2026-03-06T10:00:00Z"
}
```

#### Visibility of soft-deleted resources

- Soft-deleted resources SHOULD NOT appear in list/search results by default.
- Provide `GET /accounts?includeDeleted=true` or `GET /accounts?filters=status eq "DELETED"` to include them.
- `GET /accounts/123` for a soft-deleted resource SHOULD return `200 OK` with the resource state, or `410 Gone` if your API hides them from individual GETs.

#### Recovery

- If soft-deleted resources are recoverable, document the mechanism:
  - `PATCH /accounts/123` with `{ "status": "ACTIVE" }` (if status is patchable)
  - `POST /accounts/123/restore-requests`

#### Purge policy

- Document how long soft-deleted resources are retained before permanent purge.

#### Document it

In the OpenAPI operation description for DELETE endpoints, state:
- Whether the operation is a hard delete or soft delete.
- What status code and body are returned.
- How soft-deleted items appear (or don't) in list endpoints.
- Whether recovery is possible and how.
- The retention/purge policy.

**Related rules**: [#use-http-methods-correctly] DELETE semantics, [#use-standard-http-status-codes] status codes (410 Gone), [#document-implicit-filters-and-default-sorting] implicit filters (excluding deleted items).
