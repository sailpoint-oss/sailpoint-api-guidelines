These rules define the minimum query, filter, and pagination behavior that every list or search endpoint should document and implement.

## Pagination and Filtering Context

List endpoints are one of the highest-leverage places to be consistent: pagination, sorting, and
filtering shape the client experience.

**Pagination baseline expectations:**

- Always define a **stable default sort order** (pagination without stable ordering is not deterministic).
- Document defaults and limits (`limit` default and maximum).
- Make pagination behavior explicit in OpenAPI (parameters, response shape, examples).

**Recommended contracts:**

- Keep offset pagination (`limit`/`offset`) as the baseline — see [#support-offset-pagination] for the canonical envelope.
- If you expect large or volatile datasets, consider cursor pagination; keep cursors **opaque and stable**.

**Filtering and searching:**

- Prefer straightforward equality and set membership filters for common use cases.
- If you need complex queries, document the query language clearly and provide examples.
- Avoid breaking changes: adding filters is typically safe; changing semantics is not.

Every list endpoint should make these answers obvious:

- How do I page through results?
- What ordering is used when I do not specify one?
- Which filters and sort fields are actually supported?

## Query Parameters & Pagination
### use-standard-query-params
<RuleHeader
  id="use-standard-query-params"
  level="MUST"
  title="Use Conventional Query Parameters"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?limit=50&offset=0&filters=status eq "ACTIVE"&sorters=name:asc`,
    },
  ]}
/>

- APIs MUST use consistent query parameter names across all endpoints:
  - `limit` + `offset` for offset-based pagination (see [#support-offset-pagination]).
  - `count` (boolean) when supporting a total count — be explicit about cost/performance.
  - `filters` for filter expressions and `sorters` for ordering (see [#use-consistent-query-format]).
- Every endpoint MUST document its allowed fields (whitelist) for filtering and sorting.
- Avoid inventing per-endpoint bespoke query DSLs.
- Prefer OpenAPI-defined encoding for multi-valued parameters (`style`/`explode`) (see [#define-array-params]).

```http
GET /accounts?limit=50&offset=0&filters=status eq "ACTIVE"&sorters=name:asc
```

### define-array-params
<RuleHeader
  id="define-array-params"
  level="MUST"
  title="Define Collection Formats for Header and Query Parameters"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `parameters:
  - in: query
    name: status
    required: false
    schema:
      type: array
      items:
        type: string
    style: form
    explode: true`,
    },
  ]}
/>

- For multi-valued query params, MUST pick one canonical encoding per parameter: repeated (`?status=ACTIVE&status=DISABLED`) or comma-separated (`?status=ACTIVE,DISABLED`).
- Do not accept multiple encodings unless explicitly documented.
- Every OpenAPI parameter definition MUST include `style` and `explode` so there is no ambiguity.

Repeated parameters (`style: form`, `explode: true`):

```yaml
parameters:
  - in: query
    name: status
    required: false
    schema:
      type: array
      items:
        type: string
    style: form
    explode: true
```

Comma-separated (`style: form`, `explode: false`):

```yaml
parameters:
  - in: query
    name: status
    required: false
    schema:
      type: array
      items:
        type: string
    style: form
    explode: false
```

### support-offset-pagination
<RuleHeader
  id="support-offset-pagination"
  level="MUST"
  title="Support Offset Pagination for List Endpoints"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }, { href: "https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api", label: "GitHub REST API Pagination" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "items": [{ "id": "A" }, { "id": "B" }],
  "limit": 2,
  "offset": 0,
  "count": 123
}`,
    },
  ]}
/>

- List endpoints MUST support `limit` and `offset`. Do not ship an unpaginated list endpoint when the result set can grow beyond a trivial size.
- List endpoints MUST support **offset-based pagination** using `limit` and `offset`:
  - `limit` (integer): number of items to return. MUST document default and max.
  - `offset` (integer): number of items to skip (default 0).
  - `count` (boolean, optional): whether to include the total count when the caller asks for it.
- Responses MUST use an object wrapper with metadata:

```json
{
  "items": [{ "id": "A" }, { "id": "B" }],
  "limit": 2,
  "offset": 0,
  "count": 123
}
```

- **Do not** document or implement list responses as a bare JSON array at the root (`[ {...}, {...} ]`). The root MUST remain an object so pagination metadata can be added without breaking clients (see [#use-object-responses]). Examples in OpenAPI, guides, and SDK snippets MUST match the envelope you return in production.

- MUST define a stable, deterministic default sort order — otherwise pagination produces duplicates or missed records.
- If `offset` is beyond the available result set, return `200 OK` with an empty `items` array rather than `404`.
- If `count` is omitted or `false`, the response MAY omit the `count` field. If included, `count` MUST represent the total result size for the current filter set.
- SHOULD document performance characteristics (maximum supported `offset`, cost of `count=true`).

Declare a reusable `PagedResponse` schema and reference it from every list operation:

```yaml
components:
  schemas:
    PagedResponse:
      type: object
      required: [items, limit, offset]
      properties:
        items:
          type: array
          items: {}
          description: Items in the current page.
        limit:
          type: integer
          minimum: 1
        offset:
          type: integer
          minimum: 0
        count:
          type: integer
          minimum: 0
          description: Optional total count for the current filter set when requested.
```

#### Cursor-based pagination (optional complement)

- APIs MAY additionally offer cursor-based pagination for endpoints where offset performance degrades at scale or data is highly mutable.
- If cursor pagination is offered, **offset+limit MUST still be supported on the same endpoint** — cursor is an addition, never a replacement.
- Use `cursor` (opaque string token) in requests and `nextCursor` (opaque string, present when more results exist) in responses.
- Cursor tokens MUST be opaque, tied to the same filter and sorter context, and treated as short-lived pagination state rather than a public contract:

```json
{
  "items": [{ "id": "A" }, { "id": "B" }],
  "limit": 2,
  "count": 123,
  "nextCursor": "eyJpZCI6IkIifQ=="
}
```

**Related rules**: [#use-object-responses], [#use-standard-query-params], [#include-pagination-links].

## Query Conventions
### document-default-query
<RuleHeader
  id="document-default-query"
  level="MUST"
  title="Document Implicit Filters and Default Sorting"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "text",
      code: `If \`sorters\` is omitted, results are ordered by \`createdAt:desc\` (ties broken by \`id:asc\`).`,
    },
  ]}
/>

- List/search endpoints MUST document any implicit constraints that affect which items appear (e.g., tenant scoping, RBAC/ABAC visibility, soft-delete exclusion, lifecycle-state filtering).
- List/search endpoints MUST document the default ordering when the caller doesn't specify sorters.

#### Implicit filtering

- In the OpenAPI operation description, explicitly state all implicit constraints.
- If behavior depends on the caller's authorization, say so clearly.
- Where possible, expose parameters to control the behavior (e.g., `includeDeleted=true`) and document the defaults.

#### Default sorting

- If the caller doesn't provide a sorter, the API MUST apply **exactly one documented default ordering policy**.
- The default ordering MUST be deterministic and stable enough for pagination.
- It MAY be multi-field for tie-breaking (e.g., `createdAt desc, id asc`), but document it as a single policy.

> If `sorters` is omitted, results are ordered by `createdAt:desc` (ties broken by `id:asc`).

**Related rules**: [#use-standard-query-params], [#support-offset-pagination], [#use-consistent-query-format]

### use-consistent-query-format
<RuleHeader
  id="use-consistent-query-format"
  level="MUST"
  title="Use One Query Format Across the API"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?filters=status eq "ACTIVE"&sorters=createdAt:desc&limit=50&offset=0`,
    },
  ]}
/>

- APIs MUST use a single, consistent query format across all endpoints:
  - `filters` for filter expressions
  - `sorters` for ordering
  - `limit`/`offset` for pagination (see [#support-offset-pagination])
- The grammar for `filters` and `sorters` MUST be consistent across endpoints.
- Every endpoint MUST document its allowed field list for filtering and sorting.

#### Simple queries via query parameters (GET)

```http
GET /accounts?filters=status eq "ACTIVE"&sorters=createdAt:desc&limit=50&offset=0
```

#### Complex queries via POST search endpoint

When queries exceed practical URL length or complexity, use `POST /{resource}/search` with read-only search semantics.

- MUST clearly document "search semantics; no creation."
- MUST be safe to retry (see [#prefer-idempotent-writes], [#support-idempotency-key]).
- MUST use a single standard request body shape across all search endpoints.

```http
POST /accounts/search
Content-Type: application/json

{
  "filters": [
    { "field": "status", "op": "eq", "value": "ACTIVE" },
    { "field": "createdAt", "op": "gte", "value": "2025-01-01T00:00:00Z" }
  ],
  "sorters": [{ "field": "createdAt", "direction": "desc" }],
  "limit": 50,
  "offset": 0
}
```

**Related rules**: [#use-standard-query-params], [#define-array-params], [#document-default-query]

## Batch Operations
### design-batch-endpoints
<RuleHeader
  id="design-batch-endpoints"
  level="SHOULD"
  title="Design Batch Request Endpoints"
  externalDocs={[{ href: "https://google.aip.dev/233", label: "Google AIP-233: Batch Methods" }, { href: "https://learn.microsoft.com/en-us/graph/json-batching", label: "Microsoft Graph: JSON Batching" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "items": [
    { "name": "Account A", "sourceId": "source-1" },
    { "name": "Account B", "sourceId": "source-1" },
    { "name": "Account C", "sourceId": "source-2" }
  ]
}`,
    },
  ]}
/>

For resources where clients commonly operate on multiple items at once, APIs SHOULD provide batch endpoints.

#### Standard batch request shape

Use a consistent request shape with an `items` array:

```http
POST /accounts/batch
Content-Type: application/json
```

```json
{
  "items": [
    { "name": "Account A", "sourceId": "source-1" },
    { "name": "Account B", "sourceId": "source-1" },
    { "name": "Account C", "sourceId": "source-2" }
  ]
}
```

#### Batch size limits

- MUST document the maximum number of items per batch request (reasonable default: 50-100).
- When the limit is exceeded, return `400 Bad Request` with a clear error message stating the limit.
- MUST NOT silently truncate.

#### Processing semantics

Choose one processing model and document it explicitly:

- **All-or-nothing (transactional)**: all items succeed or all fail. Return a single status code. Preferred when items are interdependent.
- **Partial success (best-effort)**: each item processed independently. Return per-item results using `207 Multi-Status` or `200` with per-item outcomes (see [#use-per-item-batch-status]). Preferred when items are independent.

Most batch endpoints SHOULD use partial-success semantics.

#### Batch response (partial success)

```json
{
  "items": [
    { "index": 0, "status": 201, "id": "acct-001", "name": "Account A" },
    { "index": 1, "status": 201, "id": "acct-002", "name": "Account B" },
    { "index": 2, "status": 409, "error": { "title": "Conflict", "detail": "Account with this name already exists." } }
  ]
}
```

- Include the `index` to let clients correlate responses with their request items.

#### operationId convention

Follow `batch<Action><ResourcePlural>` — e.g., `batchCreateAccounts`, `batchDeleteAccounts`, `batchUpdateAccounts`.

**Related rules**: [#use-per-item-batch-status] per-item batch results, [#support-async-operations] async for very large operations, [#document-size-limits] request size limits.

## Response Metadata

### include-pagination-links
<RuleHeader
  id="include-pagination-links"
  level="SHOULD"
  title="Include Pagination Links in Collection Responses"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc8288", label: "RFC 8288 — Web Linking" }, { href: "https://jsonapi.org/format/#fetching-pagination", label: "JSON:API Pagination" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "items": [
    { "id": "C", "name": "Account C" },
    { "id": "D", "name": "Account D" }
  ],
  "limit": 2,
  "offset": 2,
  "count": 10,
  "links": {
    "self": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=2",
    "next": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=4",
    "prev": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=0"
  }
}`,
    },
  ]}
/>

- Collection responses SHOULD include a `links` object with absolute URLs for navigating the result set.
- Links complement — but do not replace — the `limit`, `offset`, and `count` fields required by [#support-offset-pagination].

#### Standard link relations

| Relation | Description | When to include |
|---|---|---|
| `self` | The URL that produced this response | Always |
| `next` | The next page of results | When more results exist |
| `prev` | The previous page of results | When `offset > 0` |

#### Offset pagination example

```http
GET /accounts?limit=2&offset=2
```

```json
{
  "items": [
    { "id": "C", "name": "Account C" },
    { "id": "D", "name": "Account D" }
  ],
  "limit": 2,
  "offset": 2,
  "count": 10,
  "links": {
    "self": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=2",
    "next": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=4",
    "prev": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=0"
  }
}
```

- Links MUST be absolute URLs (not relative paths).
- MUST preserve all original query parameters (filters, sorters) in link URLs — only change the pagination parameter.
- Omit `next` on the last page. Omit `prev` on the first page.
- Teams MAY also include `first` and `last` links if the endpoint can compute them efficiently.

#### Cursor pagination example

Cursor-based pagination is typically forward-only, so `prev` is usually omitted:

```json
{
  "items": [{ "id": "E" }, { "id": "F" }],
  "limit": 2,
  "nextCursor": "eyJpZCI6IkYifQ==",
  "links": {
    "self": "https://api.sailpoint.com/v2026/accounts?limit=2&cursor=eyJpZCI6IkQifQ==",
    "next": "https://api.sailpoint.com/v2026/accounts?limit=2&cursor=eyJpZCI6IkYifQ=="
  }
}
```

If an endpoint supports both offset and cursor, return envelope fields for both so clients can pick the pattern that fits their workload. When a `cursor` is present the server paginates from the cursor; otherwise it paginates from `offset`.
