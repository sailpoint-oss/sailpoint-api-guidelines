These rules define request/query conventions (filtering, sorting, pagination) so list/search endpoints are consistent across APIs.

## Pagination and Filtering Context

List endpoints are one of the highest-leverage places to be consistent: pagination, sorting, and
filtering shape the client experience.

**Pagination baseline expectations:**

- Always define a **stable default sort order** (pagination without stable ordering is not deterministic).
- Document defaults and limits (`limit` default and maximum).
- Make pagination behavior explicit in OpenAPI (parameters, response shape, examples).

**Recommended contracts:**

- Start with [Pagination recipes](/docs/appendices/pagination-recipes) for concrete request/response shapes.
- If you expect large or volatile datasets, consider cursor pagination; keep cursors **opaque and stable**.

**Filtering and searching:**

- Prefer straightforward equality and set membership filters for common use cases.
- If you need complex queries, document the query language clearly and provide examples.
- Avoid breaking changes: adding filters is typically safe; changing semantics is not.

**Reference**: [Pagination recipes](/docs/appendices/pagination-recipes) | [Review checklist](/docs/appendices/review-checklist)

## Query Parameters & Pagination
### #600 - Use Conventional Query Parameters
<RuleHeader id="600" level="MUST" title="Use Conventional Query Parameters" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]} />

- APIs MUST use consistent query parameter names across all endpoints:
  - `limit` + `offset` for offset-based pagination (see [#602]).
  - `count` (boolean) when supporting a total count — be explicit about cost/performance.
  - `filters` for filter expressions and `sorters` for ordering (see [#604]).
- Every endpoint MUST document its allowed fields (whitelist) for filtering and sorting.
- Avoid inventing per-endpoint bespoke query DSLs.
- Prefer OpenAPI-defined encoding for multi-valued parameters (`style`/`explode`) (see [#601]).

```http
GET /accounts?limit=50&offset=0&filters=status eq "ACTIVE"&sorters=name:asc
```

### #601 - Define Collection Formats for Header and Query Parameters
<RuleHeader id="601" level="MUST" title="Define Collection Formats for Header and Query Parameters" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- For multi-valued query params, MUST pick one canonical encoding per parameter: repeated (`?status=ACTIVE&status=DISABLED`) or comma-separated (`?status=ACTIVE,DISABLED`).
- Do not accept multiple encodings unless explicitly documented.
- Every OpenAPI parameter definition MUST include `style` and `explode` so there is no ambiguity.

Repeated parameters (`style: form`, `explode: true`):

```yaml
parameters:
  - in: query
    name: status
    required: false
    schema:
      type: array
      items:
        type: string
    style: form
    explode: true
```

Comma-separated (`style: form`, `explode: false`):

```yaml
parameters:
  - in: query
    name: status
    required: false
    schema:
      type: array
      items:
        type: string
    style: form
    explode: false
```

### #602 - Support Offset Pagination for List Endpoints
<RuleHeader id="602" level="MUST" title="Support Offset Pagination for List Endpoints" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }, { href: "https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api", label: "GitHub REST API Pagination" }]} />

- List endpoints MUST support **offset-based pagination** using `limit` and `offset`:
  - `limit` (integer): number of items to return. MUST document default and max.
  - `offset` (integer): number of items to skip (default 0).
  - `count` (boolean, optional): whether to include total count.
- Responses MUST use an object wrapper with metadata:

```json
{
  "items": [{ "id": "A" }, { "id": "B" }],
  "limit": 2,
  "offset": 0,
  "count": 123
}
```

- MUST define a stable, deterministic default sort order — otherwise pagination produces duplicates or missed records.
- SHOULD document performance characteristics (maximum supported `offset`, cost of `count=true`).

#### Cursor-based pagination (optional complement)

- APIs MAY additionally offer cursor-based pagination for endpoints where offset performance degrades at scale or data is highly mutable.
- If cursor pagination is offered, **offset+limit MUST still be supported on the same endpoint** — cursor is an addition, never a replacement.
- Use `cursor` (opaque string token) in requests and `nextCursor` (opaque string, present when more results exist) in responses:

```json
{
  "items": [{ "id": "A" }, { "id": "B" }],
  "limit": 2,
  "count": 123,
  "nextCursor": "eyJpZCI6IkIifQ=="
}
```

**Related rules**: [#204], [#600]. See also [Pagination recipes](/docs/appendices/pagination-recipes) for both patterns.

## Query Conventions
### #603 - Document Implicit Filters and Default Sorting
<RuleHeader id="603" level="MUST" title="Document Implicit Filters and Default Sorting" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]} />

- List/search endpoints MUST document any implicit constraints that affect which items appear (e.g., tenant scoping, RBAC/ABAC visibility, soft-delete exclusion, lifecycle-state filtering).
- List/search endpoints MUST document the default ordering when the caller doesn't specify sorters.

#### Implicit filtering

- In the OpenAPI operation description, explicitly state all implicit constraints.
- If behavior depends on the caller's authorization, say so clearly.
- Where possible, expose parameters to control the behavior (e.g., `includeDeleted=true`) and document the defaults.

#### Default sorting

- If the caller doesn't provide a sorter, the API MUST apply **exactly one documented default ordering policy**.
- The default ordering MUST be deterministic and stable enough for pagination.
- It MAY be multi-field for tie-breaking (e.g., `createdAt desc, id asc`), but document it as a single policy.

> If `sorters` is omitted, results are ordered by `createdAt:desc` (ties broken by `id:asc`).

**Related rules**: [#600], [#602], [#604]

### #604 - Use One Query Format Across the API
<RuleHeader id="604" level="MUST" title="Use One Query Format Across the API" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]} />

- APIs MUST use a single, consistent query format across all endpoints:
  - `filters` for filter expressions
  - `sorters` for ordering
  - `limit`/`offset` for pagination (see [#602])
- The grammar for `filters` and `sorters` MUST be consistent across endpoints.
- Every endpoint MUST document its allowed field list for filtering and sorting.

#### Simple queries via query parameters (GET)

```http
GET /accounts?filters=status eq "ACTIVE"&sorters=createdAt:desc&limit=50&offset=0
```

#### Complex queries via POST search endpoint

When queries exceed practical URL length/complexity, use `POST /{resource}/search` with **GET-like semantics** (no resource creation).

- MUST clearly document "search semantics; no creation."
- MUST be safe to retry (see [#409], [#410]).
- MUST use a single standard request body shape across all search endpoints.

```http
POST /accounts/search
Content-Type: application/json

{
  "filters": [
    { "field": "status", "op": "eq", "value": "ACTIVE" },
    { "field": "createdAt", "op": "gte", "value": "2025-01-01T00:00:00Z" }
  ],
  "sorters": [{ "field": "createdAt", "direction": "desc" }],
  "limit": 50,
  "offset": 0
}
```

**Related rules**: [#600], [#601], [#603]

## Batch Operations
### #605 - Design Batch Request Endpoints
<RuleHeader id="605" level="SHOULD" title="Design Batch Request Endpoints" externalDocs={[{ href: "https://google.aip.dev/233", label: "Google AIP-233: Batch Methods" }, { href: "https://learn.microsoft.com/en-us/graph/json-batching", label: "Microsoft Graph: JSON Batching" }]} />

For resources where clients commonly operate on multiple items at once, APIs SHOULD provide batch endpoints.

#### Standard batch request shape

Use a consistent request shape with an `items` array:

```http
POST /accounts/batch
Content-Type: application/json
```

```json
{
  "items": [
    { "name": "Account A", "sourceId": "source-1" },
    { "name": "Account B", "sourceId": "source-1" },
    { "name": "Account C", "sourceId": "source-2" }
  ]
}
```

#### Batch size limits

- MUST document the maximum number of items per batch request (reasonable default: 50-100).
- When the limit is exceeded, return `400 Bad Request` with a clear error message stating the limit.
- MUST NOT silently truncate.

#### Processing semantics

Choose one processing model and document it explicitly:

- **All-or-nothing (transactional)**: all items succeed or all fail. Return a single status code. Preferred when items are interdependent.
- **Partial success (best-effort)**: each item processed independently. Return per-item results using `207 Multi-Status` or `200` with per-item outcomes (see [#405]). Preferred when items are independent.

Most batch endpoints SHOULD use partial-success semantics.

#### Batch response (partial success)

```json
{
  "items": [
    { "index": 0, "status": 201, "id": "acct-001", "name": "Account A" },
    { "index": 1, "status": 201, "id": "acct-002", "name": "Account B" },
    { "index": 2, "status": 409, "error": { "title": "Conflict", "detail": "Account with this name already exists." } }
  ]
}
```

- Include the `index` to let clients correlate responses with their request items.

#### operationId convention

Follow `batch<Action><ResourcePlural>` — e.g., `batchCreateAccounts`, `batchDeleteAccounts`, `batchUpdateAccounts`.

**Related rules**: [#405] per-item batch results, [#407] async for very large operations, [#414] request size limits.

## Response Metadata

### #606 - Include Pagination Links in Collection Responses
<RuleHeader id="606" level="SHOULD" title="Include Pagination Links in Collection Responses" externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc8288", label: "RFC 8288 — Web Linking" }, { href: "https://jsonapi.org/format/#fetching-pagination", label: "JSON:API Pagination" }]} />

- Collection responses SHOULD include a `links` object with absolute URLs for navigating the result set.
- Links complement — but do not replace — the `limit`, `offset`, and `count` fields required by [#602].

#### Standard link relations

| Relation | Description | When to include |
|---|---|---|
| `self` | The URL that produced this response | Always |
| `next` | The next page of results | When more results exist |
| `prev` | The previous page of results | When `offset > 0` |

#### Offset pagination example

```http
GET /accounts?limit=2&offset=2
```

```json
{
  "items": [
    { "id": "C", "name": "Account C" },
    { "id": "D", "name": "Account D" }
  ],
  "limit": 2,
  "offset": 2,
  "count": 10,
  "links": {
    "self": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=2",
    "next": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=4",
    "prev": "https://api.sailpoint.com/v2026/accounts?limit=2&offset=0"
  }
}
```

#### Implementation notes

- Links MUST be absolute URLs (not relative paths).
- MUST preserve all original query parameters (filters, sorters) in link URLs — only change the pagination parameter.
- Omit `next` on the last page. Omit `prev` on the first page.
- Teams MAY also include `first` and `last` links if the endpoint can compute them efficiently.

See [Pagination recipes](/docs/appendices/pagination-recipes) for complete examples.

**Related rules**: [#204] top-level JSON objects, [#600] conventional query parameters, [#602] offset pagination, [#805] common field names.
