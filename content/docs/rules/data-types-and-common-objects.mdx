## Data Types & Formats
### use-iso8601-durations
<RuleHeader
  id="use-iso8601-durations"
  level="SHOULD"
  title="Use ISO 8601 Durations and Intervals"
  externalDocs={[{ href: "https://www.iso.org/iso-8601-date-and-time-format.html", label: "ISO 8601" }]}
  examples={[
    {
      lang: "json",
      code: `{ "timeout": "PT15M", "retention": "P7D" }`,
    },
  ]}
/>

- APIs SHOULD represent durations and time intervals using ISO 8601 format.
- Common patterns: `PT15M` (15 minutes), `PT1H30M` (1 hour 30 minutes), `P7D` (7 days).
- ❌ `900` (ambiguous unit)
- ❌ `1h30m` (non-standard)

### use-standard-dates
<RuleHeader
  id="use-standard-dates"
  level="MUST"
  title="Use Standard Date/Time Formats"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc3339", label: "RFC 3339 — Date and Time on the Internet" }, { href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }]}
  examples={[
    {
      lang: "json",
      code: `{ "createdAt": "2026-01-15T14:30:00Z", "birthDate": "2026-01-15" }`,
    },
  ]}
/>

#### JSON payloads

- Date-time values MUST use RFC 3339 / ISO 8601 strings (OpenAPI `format: date-time`). Prefer UTC (`Z` suffix).
  - ✅ `2026-01-15T14:30:00Z`
  - ✅ `2026-01-15T14:30:00.123Z`
  - ⚠ `2025-10-15T14:30:00-05:00` (allowed, but prefer UTC)
  - ❌ `01/15/2026 2:30pm`
- Date-only values MUST use `YYYY-MM-DD` (OpenAPI `format: date`).
  - ✅ `2026-01-15`
  - ❌ `15-01-2026`

#### HTTP headers

- Date/time values in HTTP headers MUST use IMF-fixdate per RFC 9110:

```http
Last-Modified: Tue, 15 Jan 2026 14:30:00 GMT
```

#### Precision

- Be consistent about fractional-second precision across endpoints — don't sometimes include `.123` and sometimes omit it.

#### OpenAPI example

```yaml
createdAt:
  type: string
  format: date-time
birthDate:
  type: string
  format: date
```

### use-standard-codes
<RuleHeader
  id="use-standard-codes"
  level="MUST"
  title="Use Standard Country, Language, and Currency Codes"
  externalDocs={[{ href: "https://www.iso.org/iso-3166-country-codes.html", label: "ISO 3166-1 Country Codes" }, { href: "https://www.rfc-editor.org/rfc/bcp/bcp47.txt", label: "BCP 47 — Language Tags" }, { href: "https://www.iso.org/iso-4217-currency-codes.html", label: "ISO 4217 Currency Codes" }]}
  examples={[
    {
      lang: "json",
      code: `{ "countryCode": "US", "languageTag": "en-US", "currency": "USD" }`,
    },
  ]}
/>

- APIs MUST use the appropriate standard for each type of code:
  - **Country codes**: ISO 3166-1 alpha-2 (e.g., `US`, `DE`)
  - **Language tags**: BCP 47 (e.g., `en-US`, `de-DE`)
  - **Currency codes**: ISO 4217 (e.g., `USD`, `EUR`)
- In OpenAPI, document which standard applies so consumers and tooling can validate.

```yaml
countryCode:
  type: string
  description: ISO 3166-1 alpha-2 country code.
  example: US
languageTag:
  type: string
  description: BCP 47 language tag.
  example: en-US
currency:
  type: string
  description: ISO 4217 currency code.
  example: USD
```

### define-number-formats
<RuleHeader
  id="define-number-formats"
  level="MUST"
  title="Define Numeric Formats"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `count:
  type: integer
  format: int32
amount:
  type: string
  description: Decimal string.
  example: "123.45"
resourceId:
  type: string
  format: uuid`,
    },
  ]}
/>

- Numeric fields MUST be modeled with explicit OpenAPI types and formats.

#### Integers

- Use `type: integer` with `format: int32` or `format: int64`.

#### Floating point

- Use `type: number` with `format: float` or `format: double` only when floating-point precision is acceptable.

#### Decimals and money

- Do NOT use floating-point for money or high-precision decimals. Use `type: string` with a documented decimal format and always provide examples.

#### IDs and opaque identifiers

- Never model IDs as numbers — use `type: string` to avoid precision loss in JavaScript.

#### OpenAPI example

```yaml
count:
  type: integer
  format: int32
sizeBytes:
  type: integer
  format: int64
ratio:
  type: number
  format: double
amount:
  type: string
  description: Decimal string.
  example: "123.45"
resourceId:
  type: string
  format: uuid
```

## Common Fields & Standard Formats
### use-common-fields
<RuleHeader
  id="use-common-fields"
  level="MUST"
  title="Use Common Field Names"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/standard_fields", label: "Google API Standard Fields" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "id": "abc-123",
  "name": "Engineering",
  "createdAt": "2026-01-15T14:30:00Z",
  "modifiedAt": "2026-02-01T09:00:00Z",
  "enabled": true,
  "ownerRef": { "id": "u-42", "name": "Alice" }
}`,
    },
  ]}
/>

- APIs MUST reuse common field names and semantics for shared concepts. Baseline field registry:
  - `id` (string): stable identifier for the resource (see [#use-url-safe-ids])
  - `name` (string): human-readable display name
  - `description` (string): human-readable description (optional)
  - `createdAt` (string, date-time): creation timestamp (RFC 3339; see [#use-standard-dates])
  - `modifiedAt` (string, date-time): last-modified timestamp (RFC 3339; see [#use-standard-dates])
  - `type` (string): discriminator/type label when needed
  - `status` (string/enum): lifecycle status (see [#use-upper-snake-enums])
  - `enabled` (boolean): true/false only (see [#use-booleans], [#use-positive-booleans])
  - `externalId` (string): external system identifier (see [#use-secondary-idempotency-keys])
  - `tags` (array of strings): user-defined categorization labels
  - `etag` (string): entity version tag for optimistic locking (see [#use-optimistic-locking])
  - `deletedAt` (string, date-time, nullable): soft-delete timestamp (see [#model-nullability] if `null` is used)
  - `href` or `self` (string, uri): canonical self-link URL
  - `ownerRef` (object: `{ id, name }`): standard reference shape for related entities
- Do not invent synonyms (`created` vs `createdAt`, `lastModified` vs `modifiedAt`). Prefer the standard name for all new APIs and fields.
- Teams SHOULD define a standard `Ref` shape (e.g., `{ "id": "...", "name": "..." }`) and reuse it for all entity references (`ownerRef`, `sourceRef`, `creatorRef`).
- For money-like values, use `amount` as a decimal string (see [#define-number-formats]) and `currency` as ISO 4217 (see [#use-standard-codes]).

### use-standard-formats
<RuleHeader
  id="use-standard-formats"
  level="MUST"
  title="Use Standard Property Formats"
  externalDocs={[{ label: "RFC 3339 — Date and Time on the Internet", href: "https://www.rfc-editor.org/rfc/rfc3339" }, { label: "IANA Media Types Registry", href: "https://www.iana.org/assignments/media-types/media-types.xhtml" }]}
  examples={[
    {
      lang: "yaml",
      code: `createdAt:
  type: string
  format: date-time
email:
  type: string
  format: email
callbackUrl:
  type: string
  format: uri
requestId:
  type: string
  format: uuid`,
    },
  ]}
/>

- APIs MUST use standardized OpenAPI formats where they apply, and SHOULD validate them at runtime.
- Use `format` only when it accurately describes the values emitted and accepted, and always provide matching examples.
- Common formats:
  - `date-time` / `date` (see [#use-standard-dates] for the canonical date/time rules)
  - `uuid` for UUID strings
  - `uri` for absolute URIs; `uri-reference` when relative references are allowed
  - `email` for email addresses
  - `ipv4` / `ipv6` for IP literals
- If a field must be constrained beyond what `format` provides, add explicit constraints (`minLength`, `maxLength`, `pattern`).

```yaml
type: object
properties:
  createdAt:
    type: string
    format: date-time
  email:
    type: string
    format: email
  callbackUrl:
    type: string
    format: uri
  requestId:
    type: string
    format: uuid
```

### encode-binary
<RuleHeader
  id="encode-binary"
  level="MUST"
  title="Encode Embedded Binary Safely"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc4648", label: "RFC 4648 — Base16, Base32, Base64 Data Encodings" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "contentType": "image/png",
  "encoding": "base64",
  "data": "iVBORw0KGgoAAAANSUhEUg..."
}`,
    },
  ]}
/>

Prefer dedicated upload/download endpoints over embedding binary in JSON (see [#use-non-json-media-types]).

- If embedding is unavoidable, APIs MUST use standard base64 encoding. Use base64url only when the value must be URL-safe.
- MUST include metadata so clients can interpret the value: `contentType`, `encoding` (`base64` or `base64url`), and optionally `sizeBytes`.
- Document the maximum allowed size and reject oversize payloads with a clear error.

```json
{
  "contentType": "image/png",
  "encoding": "base64",
  "data": "iVBORw0KGgoAAAANSUhEUg..."
}
```
