---
title: "Lifecycle & Compatibility"
description: Rules for versioning, deprecation, and safe evolution without breaking clients.
---

Use these rules when changing an existing API, introducing a new version, or marking something as experimental or deprecated.

Use this section to answer:

- Is this change compatible inside the current version line?
- If not, what is the versioning or migration path?
- How long can experimental behavior stay in that state?

---

## Backward Compatibility
### no-breaking-changes
<RuleHeader id="no-breaking-changes" level="MUST" title="Do Not Break Compatibility" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]} />

Within the same major version, changes MUST remain backward compatible.

#### Breaking changes (avoid within a major version)

- Removing or renaming endpoints, fields, enum values, or query parameters.
- Changing a field type or shape (e.g., `string` to `object`, array to object).
- Changing formats or constraints in a way that rejects previously valid data (tighter regex, smaller max length, new required fields).
- Tightening request validation when clients may already be sending additional fields.
- Changing default behavior in a visible way (sorting, pagination defaults, implicit filters).
- Changing authorization requirements for existing operations without a compatible migration path.
- Changing error contracts in a way that breaks parsing or branching.

#### Safe changes within a major version

- Adding new optional response fields.
- Adding new endpoints.
- Adding new optional request fields with safe defaults.
- Adding new enum values, but only if clients are prepared to handle unknowns (see [#tolerate-extensions]).

When in doubt, treat a visible behavior change as breaking and require a migration plan.

### classify-compatibility-by-layer
<RuleHeader
  id="classify-compatibility-by-layer"
  level="MUST"
  title="Classify Compatibility by Contract Layer"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
/>

Classify every change at each layer it affects: HTTP/REST behavior, OpenAPI specification, SDK generation, and documentation. A change that is non-breaking at the HTTP layer can still be breaking at the SDK layer; both matter. `Conditional` means the change may be safe for some consumers but breaking for others — default to conservative handling unless you have evidence the impacted clients are tolerant.

##### HTTP / REST behavior

| Change | Classification | Reasoning |
| --- | --- | --- |
| Remove or rename a path | BREAKING | Existing callers receive `404`. |
| Add a new path or HTTP method | Non-breaking | Additive. |
| Change HTTP method on existing path (`POST` → `PUT`) | BREAKING | Existing callers receive `405`. |
| Change a successful response status code (`200` → `201`) | BREAKING | Clients checking status codes may fail. |
| Add a new error status code | Conditional | Breaking if clients treat unknown codes as success. |
| Add a required query, path, header, or body parameter | BREAKING | Existing calls missing the parameter fail. |
| Add an optional query parameter or body field | Non-breaking | Existing calls remain valid. |
| Remove or rename any parameter or field (required or optional) | BREAKING | Equivalent to remove + add. |
| Change parameter location (`query` → `header`) | BREAKING | Clients sending in the old location are rejected. |
| Change a parameter or field type or format | BREAKING | Clients sending the old type fail. |
| Narrow validation (stricter regex, lower max) | BREAKING | Previously valid values are now rejected. |
| Widen validation (looser regex, higher max) | Non-breaking | Previously valid values remain valid. |
| Make an optional field/parameter required | BREAKING | Existing requests missing it fail. |
| Make a required field/parameter optional | Non-breaking | Existing clients already send it. |
| Remove a field from a response | BREAKING | Consumers reading that field receive missing data. |
| Add a field to a response | Conditional | Safe for lenient clients; breaking for strict deserializers. |
| Make a nullable field non-nullable | BREAKING | `null`-reliant clients break. |
| Make a non-nullable field nullable | Conditional | Clients that do not handle `null` may panic. |
| Change response `Content-Type` or remove a documented response header | BREAKING | Parsing or header-reading clients fail. |
| Add a response header | Non-breaking | Additive. |
| Add a new auth requirement to a previously open endpoint | BREAKING | Unauthenticated clients receive `401`. |
| Change auth scheme or add a required OAuth scope | BREAKING | Clients using the old scheme or scope are rejected. |
| Remove an auth requirement or a required scope | Non-breaking (usually) | Less restrictive. |

### treat-enum-changes-as-breaking
<RuleHeader
  id="treat-enum-changes-as-breaking"
  level="MUST"
  title="Treat Enum Changes Conservatively"
  externalDocs={[{ href: "https://google.aip.dev/126", label: "Google AIP-126: Enumerations" }]}
/>

| Change | HTTP/REST | SDK | Reasoning |
| --- | --- | --- | --- |
| Remove or rename an enum value | BREAKING | BREAKING | Clients sending the removed value are rejected; generated SDK constants disappear. |
| Add an enum value to a **request** field | Non-breaking | BREAKING | HTTP is fine; typed SDK consumers with exhaustive switches may fail. |
| Add an enum value to a **response** field | Conditional | BREAKING | Strict consumers may hit default branches or require code changes. |

Policy: treat adding enum values as BREAKING for organizational change management. The SDK layer makes this effectively unavoidable for typed-language consumers (see [#mark-enum-extensibility] for how to declare intent).

### protect-openapi-sdk-contracts
<RuleHeader
  id="protect-openapi-sdk-contracts"
  level="MUST"
  title="Protect OpenAPI and SDK Contracts"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
/>

| Change | Classification | Reasoning |
| --- | --- | --- |
| Change `operationId` (rename, remove, or newly add) | SDK BREAKING | `operationId` becomes the generated function name. |
| Change tags on an operation | SDK BREAKING | Tags typically control SDK package or module grouping. |
| Add or remove `deprecated: true` | Non-breaking (SDK warning) | Runtime behavior is unchanged. |
| Rename a `$ref` schema or move inline ↔ `$ref` | SDK BREAKING | The generated type name or shape changes. |
| Change `required` array in a schema | BREAKING | Validation and generated metadata change. |
| Add or remove `nullable: true` | Conditional / BREAKING | Generated pointer vs value types change; removing `nullable` can break `null`-reliant clients. |
| Change `additionalProperties` | Conditional | Unknown-field handling and generated map shapes may change. |
| Add a discriminator or change mapping | BREAKING | Generated deserialization logic changes. |
| Add or change `allOf`/`oneOf`/`anyOf` on an existing schema | BREAKING | Generated type shapes change substantially. |
| Change parameter `name`, `in`, `style`, or `explode` | BREAKING | Wire contract and generated call signatures change. |
| Change `servers[].url` or remove a server | BREAKING | Clients targeting the old server fail. |
| Remove a `securityScheme` | BREAKING | Clients using that scheme break. |

##### SDK-specific

Generated SDKs can break even when HTTP behavior is unchanged. Treat the following as SDK-breaking: `operationId` rename, schema name rename, tag change, adding `nullable`, new required parameter, parameter rename, response type change, `additionalProperties` change, new enum value, response field type change, `oneOf`/`anyOf` introduction, path parameter type change, format change (e.g., `date` → `date-time`).

##### Documentation

These do not break code, but they break the developer-experience contract: removing a documented guide or code example, changing a portal URL slug, substituting a renamed field in an example, changing a description in a way that changes semantic meaning, or removing changelog entries.

##### Quick reference

| Change | HTTP | SDK | Docs |
| --- | --- | --- | --- |
| Remove path | BREAK | BREAK | BREAK |
| Rename `operationId` | safe | BREAK | BREAK |
| Change schema name | safe | BREAK | BREAK |
| Change tag on operation | safe | BREAK | BREAK |
| Add optional field (response) | safe | safe | safe |
| Add enum value | safe | BREAK | warn |
| Remove enum value | BREAK | BREAK | BREAK |
| Rename field | BREAK | BREAK | BREAK |
| Add required parameter | BREAK | BREAK | BREAK |
| Add optional parameter | safe | COND* | safe |
| `nullable` added | safe | BREAK | warn |
| Change format | BREAK | BREAK | warn |
| Change `servers[].url` | BREAK | BREAK | BREAK |

`COND*` = breaking in positional-argument SDK generators.

### prefer-additive-changes
<RuleHeader
  id="prefer-additive-changes"
  level="SHOULD"
  title="Prefer Compatible Extensions"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
  examples={[
    {
      lang: "yaml",
      code: `# Additive: new optional field with a safe default
Account:
  type: object
  properties:
    id: { type: string }
    displayName: { type: string }
    archived: { type: boolean, default: false }`,
    },
  ]}
/>

Teams SHOULD add capabilities instead of changing existing behavior:

- Adding a new optional response field.
- Adding a new optional request field with a safe default.
- Adding a new query parameter that does not change behavior when omitted.
- Adding a new endpoint instead of overloading an existing one.

Changes that look additive can still break clients if they tighten validation or change defaults. If behavior genuinely must change, prefer a new endpoint or a new major version.

### ignore-unknown-response-fields
<RuleHeader
  id="ignore-unknown-response-fields"
  level="MUST"
  title="Ignore Unknown Response Fields"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "id": "abc",
  "newFieldClientDoesNotKnow": true
}`,
    },
  ]}
/>

Clients MUST ignore unknown fields in responses. If the server adds `newField`, existing parsing MUST keep working.

### tolerate-unknown-enum-values
<RuleHeader
  id="tolerate-unknown-enum-values"
  level="MUST"
  title="Tolerate Unknown Enum Values"
  externalDocs={[{ href: "https://google.aip.dev/126", label: "Google AIP-126: Enumerations" }]}
  examples={[
    {
      lang: "json",
      code: `{ "status": "ACTIVE_PENDING_REVIEW" }`,
    },
  ]}
/>

If a client receives an unrecognized enum value, it MUST NOT crash. Map unrecognized values to `UNKNOWN` or treat them as a safe default. See [#mark-enum-extensibility] for how APIs annotate enum extensibility.

For SDK teams: avoid generated enums that throw on unknown values. Prefer string unions or safe mapping with an `UNKNOWN` case.

### handle-undocumented-status-codes
<RuleHeader
  id="handle-undocumented-status-codes"
  level="SHOULD"
  title="Handle Undocumented HTTP Status Codes"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 503 Service Unavailable
Retry-After: 30`,
    },
  ]}
/>

If a client receives an undocumented status code, it SHOULD handle the status class correctly. For `429`, `500`, `502`, `503`, and `504`, follow retry/backoff guidance rather than failing with an unhandled exception.

### constrain-inputs
<RuleHeader
  id="constrain-inputs"
  level="SHOULD"
  title="Be Conservative with Inputs"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
  examples={[
    {
      lang: "yaml",
      code: `CreateAccountRequest:
  type: object
  required: [name]
  additionalProperties: false
  properties:
    name:
      type: string
      minLength: 1
      maxLength: 128
      pattern: "^[a-zA-Z0-9_.-]+$"`,
    },
  ]}
/>

- Teams SHOULD define and document input constraints explicitly — types, formats, length limits, required fields.
- Choose your unknown-field policy (ignore vs. reject) up front and document it. Changing from "ignore" to "reject" later is a breaking change.
- Constraints like `minLength`, `maxLength`, `format`, `pattern`, and `minimum`/`maximum` SHOULD be expressed in OpenAPI so they are machine-readable.
- If you need to tighten validation over time, do it with a migration path: warn first, document timelines, and consider new endpoints or versions.

### use-object-responses
<RuleHeader
  id="use-object-responses"
  level="MUST"
  title="Return Top-Level JSON Objects"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc8259", label: "RFC 8259 — The JSON Data Interchange Format" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "items": [{ "id": "A" }, { "id": "B" }],
  "count": 123,
  "limit": 2,
  "offset": 0
}`,
    },
  ]}
/>

Responses MUST use a JSON object as the top-level structure, not a bare array. This keeps the door open to add metadata (counts, links, paging cursors) without changing the response shape.

- ✅ List envelope: `{ "items": [ ... ], "count": 123 }`
- ✅ Later add metadata (non-breaking): `{ "items": [ ... ], "count": 123, "links": { "self": "..." } }`
- ❌ Top-level array: `[ { "id": "A" }, { "id": "B" } ]` (prevents adding metadata compatibly)

**Existing APIs and alternate envelopes**: Some services already return a bare JSON array for historical list endpoints, or use a different object wrapper (for example a `{ "data": [...] }` shape). This rule still forbids **new** list designs that use a top-level array. When evolving legacy list endpoints, prefer migrating clients to an object envelope via additive fields, a dedicated replacement endpoint, or an explicit new version—do not silently change an established array body without a compatibility plan. If you use a non-`items` envelope, document it consistently and ensure examples and schemas match production (see [#require-accurate-examples]).

For single-resource responses, return the resource object directly. For errors, use Problem Details (`application/problem+json`) (see [#use-problem-details]).

`204 No Content` is still valid for operations that intentionally return no body. Non-JSON success responses are allowed for downloads/uploads when appropriate (see [#use-non-json-media-types]), but error responses should remain JSON (Problem Details).

### treat-objects-extensible
<RuleHeader
  id="treat-objects-extensible"
  level="MUST"
  title="Treat OpenAPI Objects as Extensible"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
  examples={[
    {
      lang: "yaml",
      code: `Account:
  type: object
  additionalProperties: true
  required: [id]
  properties:
    id: { type: string }
    displayName: { type: string }`,
    },
  ]}
/>

Object schemas in responses MUST be treated as open for extension by default:

- Clients MUST ignore unknown response fields (see [#tolerate-extensions]).
- Servers MUST NOT make new fields required in existing responses.
- Enum sets MAY grow over time; clients MUST tolerate unknown enum values (see [#tolerate-extensions]).
- Servers MAY add new optional properties over time without requiring clients to upgrade.

These additive changes should not require a version bump.

## Versioning & Metadata
### avoid-version-forks
<RuleHeader id="avoid-version-forks" level="SHOULD" title="Avoid Breaking Changes as the Default Strategy" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }, { href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

- Teams SHOULD prefer additive changes first: optional fields, new endpoints, and optional query parameters with safe defaults.
- Introduce a new version only for a clear, unavoidable breaking change with a concrete migration plan.
- Do not create a new version when the same outcome could have been achieved additively.
- Do not create a new version without a deprecation or support plan for the old one.

### use-path-versioning
<RuleHeader
  id="use-path-versioning"
  level="MUST"
  title="Use Path Versioning When Versions Coexist"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "http",
      code: `GET /v2026/accounts HTTP/1.1
Host: api.sailpoint.com`,
    },
  ]}
/>

If multiple API versions must coexist, teams MUST represent the version in the URL path (URI versioning), e.g. `/v2026/...` or `/v3/...`.

- ✅ `/v2026/accounts` and `/v2027/accounts`
- ✅ `/v3/accounts` and `/v4/accounts`
- ❌ `/accounts?version=3`
- ❌ `Accept: application/vnd.company.v3+json`

Versioning is only warranted when you have unavoidable breaking changes and need old and new versions live concurrently. Prefer additive evolution when possible (see [#no-breaking-changes] and [#avoid-version-forks]).

### use-calendar-versioning
<RuleHeader
  id="use-calendar-versioning"
  level="MUST"
  title="Use Year-Based API Versioning (YYYY.Revision)"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "yaml",
      code: `info:
  title: Identity API
  version: "2026.1"
servers:
  - url: https://api.sailpoint.com/v2026`,
    },
  ]}
/>

- APIs MUST use a year-based version identifier in the form `YYYY.{revision}` (example: `2026.1`, `2026.2`).
- The `YYYY` portion identifies the major contract line. The `{revision}` increments when the published contract changes.
- If multiple versions must coexist, use URI versioning (see [#use-path-versioning]) using the year line (e.g., `/v2026/...`).
- Within a version line, avoid breaking changes (see [#no-breaking-changes]).
- Each `{revision}` MUST have a corresponding changelog entry describing contract changes and any migration or deprecation notes.
- Implementation-only changes that do not change the published contract do not require a revision bump.

## Deprecation & Sunset
### mark-deprecated
<RuleHeader
  id="mark-deprecated"
  level="MUST"
  title="Reflect Deprecation in OpenAPI"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "yaml",
      code: `paths:
  /accounts/{id}:
    get:
      deprecated: true
      summary: Get account
      x-deprecated-description: |
        Deprecated in favor of GET /v2027/accounts/{id}.
        Sunset: 2027-06-30.`,
    },
  ]}
/>

When deprecating any API element (operation, parameter, schema, field), teams MUST:

- Mark it as deprecated in OpenAPI (`deprecated: true`).
- Put **deprecation-specific** narrative in `x-deprecated-description` (vendor extension). Keep the primary `description` focused on what the operation does today so generated docs and tooling that surface `description` stay readable for consumers who have not migrated yet.
- Provide a clear migration path (replacement endpoint, field, or version).
- Publish a sunset timeline with a link to migration documentation.
- State what is deprecated, what to use instead, and by when.

```yaml
paths:
  /accounts/{id}:
    get:
      deprecated: true
      summary: Get account
      description: |
        Returns the account by ID. Behavior is unchanged for callers still on this path.
      x-deprecated-description: |
        Deprecated in favor of GET /v2027/accounts/{id}.
        Sunset: 2027-06-30. See migration: https://developer.sailpoint.com/docs
      externalDocs:
        description: Migration guide
        url: https://developer.sailpoint.com/docs
      responses:
        "200": { ... }
```

### monitor-deprecation
<RuleHeader id="monitor-deprecation" level="MUST" title="Monitor Deprecated API Usage" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

When an API element is deprecated (see [#mark-deprecated]), teams MUST monitor usage and proactively notify consumers:

- Track calls to deprecated operations (and, where feasible, deprecated parameters and fields).
- Identify calling clients by token client ID, integration identifier, or other stable identifier.
- Maintain dashboards and alerts leading up to sunset.

#### Recommended workflow

- **At deprecation**: announce the deprecation, replacement, and sunset date.
- **During migration window**: notify top callers and provide migration support.
- **Before sunset**: escalate notifications and confirm readiness.

Teams SHOULD have a playbook for contacting consumers so this process does not get reinvented every time.

### add-sunset-headers
<RuleHeader
  id="add-sunset-headers"
  level="SHOULD"
  title="Add Deprecation and Sunset Headers"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: true
Sunset: Tue, 30 Jun 2027 00:00:00 GMT

{ "id": "123", "name": "Example" }`,
    },
  ]}
/>

When an endpoint is deprecated, APIs SHOULD include `Deprecation` and `Sunset` headers in responses. These headers complement but do not replace OpenAPI `deprecated: true` and migration guidance (see [#mark-deprecated]).

### monitor-sunset-headers
<RuleHeader
  id="monitor-sunset-headers"
  level="SHOULD"
  title="Have Clients Monitor Deprecation and Sunset Headers"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#versioning", label: "Microsoft REST API Guidelines: Versioning" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 200 OK
Deprecation: true
Sunset: Tue, 30 Jun 2027 00:00:00 GMT
Link: <https://developer.sailpoint.com/docs/migration>; rel="deprecation"`,
    },
  ]}
/>

API clients SHOULD treat `Deprecation` and `Sunset` response headers as actionable signals:

- When `Deprecation` is present, log it or emit telemetry.
- When `Sunset` is present, record the sunset date and create an alert or ticket.
- For SDKs and shared client libraries, provide a common hook or middleware so application teams do not need to implement this repeatedly.

Presence or absence of headers MUST NOT be the only way clients learn about deprecation. Specs and docs remain canonical (see [#mark-deprecated]). Clients MUST NOT ignore server-side deprecation just because headers are missing.

### no-new-deprecated-usage
<RuleHeader id="no-new-deprecated-usage" level="MUST" title="Do Not Start New Usage of Deprecated APIs or Features" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

Teams MUST NOT start new dependencies on APIs or features that are already marked deprecated. This applies to:

- New code paths calling deprecated endpoints or fields.
- New integrations or clients adopting deprecated behavior.
- New tenants or environments enabling or onboarding onto deprecated versions.

The only exception is with explicit owner approval and a documented remediation plan that includes a timeline and migration path. Any such exceptions SHOULD be time-bounded and tracked.

## API Metadata & Version Lifecycle
### include-api-metadata
<RuleHeader
  id="include-api-metadata"
  level="MUST"
  title="Include API Metadata"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `openapi: 3.0.3
info:
  title: Identity API
  version: "2026.1"
  description: Manage identities and accounts.
  contact:
    name: Identity Platform Team
    email: identity-platform@sailpoint.com
servers:
  - url: https://api.sailpoint.com/v2026
tags:
  - name: Accounts`,
    },
  ]}
/>

OpenAPI specifications MUST include complete API metadata. Required fields:

- `info.title`: a human-friendly API name
- `info.version`: the published contract version (aligned with [#use-calendar-versioning])
- `info.description`: what the API is for, key concepts, and a link to guides
- `info.contact`: support or owner contact (team or distribution list)
- `servers`: at least one base URL (or environment template)
- `tags`: a consistent tagging strategy for operations (at least one tag per operation)

Strongly encouraged: `info.termsOfService`, `info.license`, `externalDocs`, and `info.x-audience` (see [#specify-audience]).

```yaml
openapi: 3.0.3
info:
  title: Identity API
  version: "2026.1"
  description: |
    Manage identities and accounts.
    See guides: https://developer.sailpoint.com/docs
  contact:
    name: Identity Platform Team
    email: identity-platform@sailpoint.com
servers:
  - url: https://api.sailpoint.com/v2026
    description: Production
  - url: https://{region}.api.sailpoint.com/v2026
    variables:
      region:
        default: us
        enum: [us, eu]
tags:
  - name: Accounts
  - name: Identities
```

### specify-audience
<RuleHeader
  id="specify-audience"
  level="MUST"
  title="Specify API Audience"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `info:
  x-audience: external-public`,
    },
  ]}
/>

- APIs MUST declare the intended audience in OpenAPI using `info.x-audience`.
- Allowed values: `internal-company` (internal-only APIs) and `external-public` (customer- and partner-facing APIs).
- The audience value affects publishing, support expectations, and compatibility rigor — teams SHOULD ensure it matches how the API is actually exposed and documented.

### follow-version-policy
<RuleHeader id="follow-version-policy" level="MUST" title="Follow Version Requirements" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

- Teams MUST NOT introduce breaking changes within a published major version line (see [#no-breaking-changes]).
- Each major version line MUST receive at least 2 years of support.
- The versioning strategy MUST be documented in the OpenAPI specification (see [#use-calendar-versioning], [#use-path-versioning]).

"Support" at minimum means:
- The version remains available and documented.
- Critical security and availability fixes MAY be applied without changing the published contract.
- A sunset/deprecation timeline is communicated for retirement (see [#mark-deprecated], [#add-sunset-headers], [#monitor-sunset-headers]).

### mark-experimental
<RuleHeader
  id="mark-experimental"
  level="MUST"
  title="Follow Experimental Requirements When Applicable"

### document-experimental-support
<RuleHeader

### agree-sunset-timelines
<RuleHeader id="agree-sunset-timelines" level="SHOULD" title="Agree on Deprecation Timeframes with Clients" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

- Teams SHOULD collaborate with known clients to agree on reasonable deprecation timeframes.
- Prefer longer windows for external and public APIs than for internal-only APIs.
- If client coordination is not possible, publish a conservative default window and provide an escalation path.

## Enum Evolution

### mark-enum-extensibility
<RuleHeader
  id="mark-enum-extensibility"
  level="SHOULD"
  title="Annotate Enum Extensibility (Open vs Closed)"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }, { href: "https://google.aip.dev/126", label: "Google AIP-126: Enumerations" }]}
  examples={[
    {
      lang: "yaml",
      code: `status:
  type: string
  x-extensible: true
  enum: [ACTIVE, INACTIVE, PENDING]`,
    },
  ]}
/>

APIs SHOULD annotate enums with their extensibility intent using the `x-extensible` vendor extension.

#### Open enums (extensible)

New values MAY be added in any minor revision without a major version bump. Clients MUST handle unknown values gracefully (see [#tolerate-extensions]).

```yaml
status:
  type: string
  x-extensible: true
  enum: [ACTIVE, INACTIVE, PENDING]
  description: >
    Account status. This enum is extensible — new values may be
    added in future revisions. Clients must handle unknown values.
```

#### Closed enums (non-extensible)

New values MUST NOT be added without a major version bump.

```yaml
httpMethod:
  type: string
  x-extensible: false
  enum: [GET, POST, PUT, PATCH, DELETE]
  description: >
    HTTP method. This enum is closed — the value set is fixed
    within this major version.
```

#### Default assumption

If `x-extensible` is not present, clients SHOULD assume the enum is **open** (extensible).

#### Compatibility rules

- Adding a value to an **open** enum is a compatible change.
- Adding a value to a **closed** enum is a breaking change and requires a new major version (see [#no-breaking-changes]).
- Removing or renaming an enum value is always a breaking change, regardless of extensibility.

#### SDK generation guidance

- For open enums, generate string unions with an `UNKNOWN` fallback (or equivalent).
- For closed enums, exhaustive enums without a fallback are acceptable.

**Related rules**: [#use-upper-snake-enums] enum naming, [#no-breaking-changes] backward compatibility, [#prefer-additive-changes] compatible extensions, [#tolerate-extensions] client resilience, [#treat-objects-extensible] extensible objects.

## Experimental Lifecycle

### timebox-experiments
<RuleHeader
  id="timebox-experiments"
  level="MUST"
  title="Time-Box Experimental APIs"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `paths:
  /accounts:
    get:
      x-stability: experimental
      x-sailpoint-experimental-expires: 2026-09-30`,
    },
  ]}
/>

If an API requires an experimental opt-in mechanism, it MUST have a documented expiration and owner.

- Document the exact opt-in mechanism and spelling in the contract and docs. If access depends on a special header, show the exact header name and expected value in examples.
- Record when the experimental period started, who owns it, and the target decision date to promote, replace, or remove it.
- Experimental state MUST NOT stay open-ended. Set an expiration no more than 180 days from first publication unless an exception is explicitly approved and documented.
- When the deadline is reached, teams MUST either promote the behavior toward GA (or another documented stability level), publish an approved extension, or remove the experimental path.
- Do not require undocumented experimental markers for behavior that otherwise looks stable.

Promotion criteria and platform-wide governance for experimental programs SHOULD be agreed with API owners and architecture stakeholders outside this document when the default windows here are not sufficient.

```yaml
paths:
  /accounts:
    get:
      description: |
        Experimental until 2026-09-30.
        Requires header X-SailPoint-Experimental: accounts-search-v2.
      x-stability: experimental
      x-sailpoint-experimental-expires: 2026-09-30
```
