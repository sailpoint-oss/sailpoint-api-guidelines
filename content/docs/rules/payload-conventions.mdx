These rules explain the payload defaults that callers should be able to rely on without guessing.

Use this section to answer:

- When is a field omitted versus returned as `null`?
- What defaults apply when an optional field is missing?
- Which media type and PATCH behavior should the contract declare?

## Boolean & Null Handling
### handle-null-values-correctly
<RuleHeader
  id="handle-null-values-correctly"
  level="MUST"
  title="Handle Null Values Correctly"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "name": "Example"
}`,
    },
  ]}
/>

- Treat `null` and absent as equivalent for optional properties unless the API explicitly documents a different meaning.
- Prefer omitting optional properties over sending `null` — `{}` is cleaner than `{ "field": null }`.
- `null` MUST NOT change the semantics relative to omission for a property unless explicitly documented.
- Booleans: if not applicable, omit rather than returning `null` (see [#use-booleans-correctly]).
- Avoid overloading `null` vs absent on the request side (e.g., "clear this value"). If you need "clear" semantics, use JSON Merge Patch (RFC 7396) or JSON Patch (RFC 6902).
- If responses contain `null` for a field, the OpenAPI spec MUST reflect that.
- If the spec does not mark a field as nullable, the runtime response MUST NOT contain `null` for it.

### use-booleans-correctly
<RuleHeader
  id="use-booleans-correctly"
  level="MUST"
  title="Use Booleans Correctly"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "json",
      code: `{ "enabled": true }`,
    },
  ]}
/>

- Boolean properties MUST never be `null`.
- Required booleans MUST be present and MUST be `true` or `false`.
- Optional booleans that are not applicable MUST be omitted entirely — do not send `null`.
- If you need three states, use an explicit enum (e.g., `"ENABLED" | "DISABLED" | "UNKNOWN"`).
- Every optional boolean MUST have documented omission behavior (see [#define-defaults-for-optional-properties]).

- ✅ `{ "enabled": true }`
- ✅ `{}` (if `enabled` is optional and not applicable)
- ❌ `{ "enabled": null }`

### initialize-empty-arrays
<RuleHeader
  id="initialize-empty-arrays"
  level="MUST"
  title="Initialize Empty Arrays"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "json",
      code: `{ "items": [] }`,
    },
  ]}
/>

- Empty collections MUST be represented as empty arrays (`[]`), not `null`.
- If the property is optional, omission is allowed, but if present it MUST be an array.
- OpenAPI schemas MUST NOT mark array properties as nullable.

- ✅ `{ "items": [] }`
- ❌ `{ "items": null }`

### model-nullable-fields-in-openapi
<RuleHeader
  id="model-nullable-fields-in-openapi"
  level="MUST"
  title="Model Nullable Fields in OpenAPI"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `middleName:
  type: string
  nullable: true`,
    },
  ]}
/>

- If an API can return or accept `null` for a field, the OpenAPI schema MUST model that.
- If `null` is not modeled in the spec, it MUST NOT appear at runtime.
- Prefer omitting optional fields rather than returning `null` (see [#handle-null-values-correctly]).
- Booleans MUST never be nullable (see [#use-booleans-correctly]). Arrays MUST never be nullable (see [#initialize-empty-arrays]).

#### OpenAPI modeling

For OpenAPI 3.0.x, use `nullable: true`. For OpenAPI 3.1.x, use JSON Schema unions (e.g., `type: [string, "null"]`).

```yaml
middleName:
  type: string
  nullable: true
```

## JSON Structure & Properties
### use-standard-non-json-media-types
<RuleHeader
  id="use-standard-non-json-media-types"
  level="MAY"
  title="Use Standard Non-JSON Media Types"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9457", label: "RFC 9457 — Problem Details" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report-123.pdf"`,
    },
  ]}
/>

- Default to JSON unless the use case genuinely needs a non-JSON representation (see [#use-standard-media-types]).
- When non-JSON content types are needed, always set the correct `Content-Type`.
- Use `Content-Disposition` for downloads when appropriate.
- Error responses SHOULD still use JSON even when the success body is non-JSON (see [#define-a-standard-error-contract-in-openapi-problem-details]).

#### File download

```http
GET /reports/123/content
Accept: application/pdf
```

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report-123.pdf"
```

#### Binary upload

```http
PUT /avatars/123
Content-Type: image/png
```

#### Large exports

For large exports, prefer an async job resource (`POST /exports` returning `202 Accepted` with a status URL, then `GET /exports/{id}` for status and a link to download). See [#support-long-running-operations] for the async job pattern.

### use-standard-media-types
<RuleHeader
  id="use-standard-media-types"
  level="SHOULD"
  title="Use Standard Media Types"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9457", label: "RFC 9457 — Problem Details" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 200 OK
Content-Type: application/json`,
    },
  ]}
/>

- APIs SHOULD use standard IANA-registered media types.
- Defaults: `application/json` for success responses, `application/problem+json` for errors (see [#define-a-standard-error-contract-in-openapi-problem-details]).
- Common non-JSON types: `application/pdf`, `text/csv`, `application/zip`, `application/octet-stream`, `multipart/form-data`.
- Always set the correct `Content-Type` for responses and require it for request bodies.
- Avoid custom/vendor media types unless you have a strong compatibility reason.
- OpenAPI specs MUST declare correct content types for all request and response bodies.

### define-maps-with-additionalproperties
<RuleHeader
  id="define-maps-with-additionalproperties"
  level="SHOULD"
  title="Define Maps with additionalProperties"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `type: object
description: Map from feature flag name to state.
additionalProperties:
  type: string`,
    },
  ]}
/>

- When representing a map/dictionary with dynamic keys in JSON, model it as an object with `additionalProperties` describing the value type.
- Document the key space: what keys mean, how they are constructed, and any constraints.
- Make it clear whether keys are stable (contracted) or arbitrary (user-provided).
- If the key set is bounded and known, use explicit properties or an array of objects instead.

#### OpenAPI examples

Map of string to string:

```yaml
type: object
description: Map from feature flag name to state.
additionalProperties:
  type: string
```

Map of string to object:

```yaml
type: object
description: Map from attribute name to attribute metadata.
additionalProperties:
  $ref: "#/components/schemas/AttributeMetadata"
```

#### When to use arrays instead

If clients need ordering, duplicates, or additional per-entry metadata, prefer an array of key-value objects:

```json
{
  "attributes": [
    { "key": "department", "value": "Engineering" },
    { "key": "region", "value": "US" }
  ]
}
```

If keys are user-provided, document any normalization rules (case sensitivity, allowed characters).

### avoid-nested-objects
<RuleHeader
  id="avoid-nested-objects"
  level="SHOULD"
  title="Avoid Nested Objects"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "id": "123",
  "ownerRef": { "id": "U1", "name": "Ada" }
}`,
    },
  ]}
/>

- APIs SHOULD minimize deeply nested object structures.
- Use references to separate resources (IDs or links) instead of embedding full graphs.
- If you embed related data, embed only a small, stable summary (e.g., `{id, name}`), not the full related object.
- Nesting is acceptable for small, intrinsic value objects that are not standalone resources (e.g., `address`, `coordinates`).
- Avoid embedding large sub-objects that make pagination, filtering, or patching difficult.

```json
{
  "id": "123",
  "ownerRef": { "id": "U1", "name": "Ada" }
}
```

- ✅ Reference with a small summary shape
- ❌ Embedding entire related graphs several levels deep

### define-defaults-for-optional-properties
<RuleHeader
  id="define-defaults-for-optional-properties"
  level="MUST"
  title="Define Defaults for Optional Properties"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `includeDisabled:
  type: boolean
  default: false`,
    },
  ]}
/>

- Optional properties MUST have documented default behavior when omitted.
- If a default is truly stable, declare it in OpenAPI using `default`.
- If a default is contextual (depends on tenant config, caller identity, or feature flags), document that explicitly in prose.
- Every optional boolean MUST have a documented default (see [#use-booleans-correctly]). Booleans MUST never be `null`.
- If omitted, the server MUST behave as if the default value was supplied.
- A reviewer reading the spec SHOULD be able to determine what happens for every optional field when omitted.

- `includeDisabled` (optional): default is `false`
- `dryRun` (optional): default is `false`

### define-required-fields-per-openapi
<RuleHeader
  id="define-required-fields-per-openapi"
  level="MUST"
  title="Define Required Fields per OpenAPI"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `type: object
required: [id, name]
properties:
  id:
    type: string
  name:
    type: string`,
    },
  ]}
/>

- APIs MUST model requiredness explicitly in OpenAPI.
- Request bodies and parameters MUST mark required inputs using OpenAPI `required` (for properties) and `required: true` (for parameters).
- Responses SHOULD also be modeled accurately: mark always-present fields as required; do not mark conditionally-present fields as required.
- When required fields differ between operations, use separate schemas (e.g., `CreateAccountRequest` vs `UpdateAccountRequest`).

```yaml
type: object
required: [id, name]
properties:
  id:
    type: string
  name:
    type: string
```

## Partial Update Conventions

### specify-patch-content-type-and-null-semantics
<RuleHeader
  id="specify-patch-content-type-and-null-semantics"
  level="MUST"
  title="Specify PATCH Content Type and Null Semantics"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc7396", label: "RFC 7396 — JSON Merge Patch" }, { href: "https://www.rfc-editor.org/rfc/rfc6902", label: "RFC 6902 — JSON Patch" }, { href: "https://www.rfc-editor.org/rfc/rfc5789", label: "RFC 5789 — PATCH Method" }]}
  examples={[
    {
      lang: "http",
      code: `PATCH /accounts/123
Content-Type: application/merge-patch+json

{ "description": "Updated", "nickname": null }`,
    },
  ]}
/>

- Every PATCH endpoint MUST declare the accepted content type in its OpenAPI `requestBody`.
- Every PATCH endpoint MUST document null vs. omission semantics explicitly.

Pick one PATCH style per endpoint and make the contract obvious to callers:

- Use JSON Merge Patch when omitted means "leave unchanged" and `null` means "clear".
- Use JSON Patch when callers need explicit operations on arrays or nested paths.
- Use a resource-specific JSON body only when the API has a small, well-documented patch contract.

#### Recognized PATCH formats

APIs MUST use one of these three approaches for each PATCH endpoint:

**1. JSON Merge Patch (RFC 7396)** — `Content-Type: application/merge-patch+json`

Send only the fields you want to change. Omitted fields are left unchanged. Sending `null` explicitly clears a field.

```http
PATCH /accounts/123
Content-Type: application/merge-patch+json

{ "description": "Updated", "nickname": null }
```

Result: `description` is updated, `nickname` is cleared, all other fields unchanged.

**2. JSON Patch (RFC 6902)** — `Content-Type: application/json-patch+json`

An array of discrete operations (`add`, `remove`, `replace`, `move`, `copy`, `test`). Supports array manipulation, positional updates, and atomic test-and-set.

```http
PATCH /accounts/123
Content-Type: application/json-patch+json

[
  { "op": "replace", "path": "/description", "value": "Updated" },
  { "op": "remove", "path": "/nickname" }
]
```

**3. Resource-specific patch schema** — `Content-Type: application/json`

A custom schema where the API defines exactly which fields are patchable. When using this format, the schema MUST document:
- Which fields are included in the patch
- Whether omitted fields are left unchanged (typical) or reset
- How `null` is handled for each nullable field

```http
PATCH /accounts/123
Content-Type: application/json

{ "description": "Updated" }
```

#### Null vs. omission semantics

Every PATCH endpoint MUST document:

1. **What does omitting a field mean?** (Almost always: "leave unchanged.")
2. **What does setting a field to `null` mean?** (Options: "clear the value," "invalid — rejected with 400," or "same as omission.")

If `null` and omission mean the same thing, state that explicitly.

#### OpenAPI modeling

Declare the content type in the `requestBody` for each PATCH operation:

```yaml
paths:
  /accounts/{accountId}:
    patch:
      summary: Update account
      requestBody:
        required: true
        content:
          application/merge-patch+json:
            schema:
              $ref: "#/components/schemas/AccountPatch"
      responses:
        "200":
          description: Updated account
```

For resource-specific patch schemas, use a separate schema (e.g., `AccountPatch`) distinct from the create schema. Do not reuse the same schema for POST and PATCH.

#### Examples

Every PATCH endpoint MUST include at least one example showing how `null` is handled:

```json
// Merge Patch: clear optional nickname, update description
{ "description": "New description", "nickname": null }

// Merge Patch: update description only, nickname unchanged
{ "description": "New description" }
```
