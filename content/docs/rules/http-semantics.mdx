title: "HTTP Semantics"
description: Rules for HTTP method correctness, status codes, headers, retries, and safe semantics.

These rules standardize method, status code, error, and retry behavior so clients can predict what the API will do from the wire contract alone.

## Error Model Context

Consistent error responses reduce client guesswork and make failures easier to diagnose and handle.

**Recommendations:**

- Use the most specific HTTP status code you can.
- Keep error payloads **stable** and **documented** in OpenAPI.
- Avoid leaking sensitive implementation details (stack traces, internal IDs, vendor exceptions).

**Problem Details (RFC 9457):**

Problem Details provides a standard JSON shape (`type`, `title`, `status`, `detail`, `instance`) while still allowing extensions.

- Use a stable `type` URI for each error category.
- Use `title` for a short human-readable category name.
- Use `detail` for request-specific details (safe to show to callers).
- Add extension fields for structured, machine-readable information (e.g., `errors[]` for field-level issues).

## Idempotency Context

Clients retry requests (network issues, timeouts, transient failures). APIs should make retries safe and predictable.

**Patterns:**

- **Optimistic locking for updates**: prefer HTTP-native optimistic locking using `ETag` + `If-Match` (or date-based preconditions when necessary).
- **Idempotency keys for safe retries**: for operations that might be retried (especially POST that creates resources), consider a client-provided `Idempotency-Key`. Server deduplicates requests with the same key for a fixed window.
- **Natural keys**: some domains have natural keys that can prevent duplicates. If used, document them explicitly and be clear about conflict behavior.

Use this section to answer:

- Which HTTP method and status code should this operation use?
- What does the standard error body look like?
- Is the operation safe to retry?

## HTTP Headers & Methods

| Method | Default use | Key requirement |
| --- | --- | --- |
| `GET` | Read data | Safe and side-effect free |
| `POST` | Create resources or submit request/search resources | `201` for creation, no hidden update semantics |
| `PUT` | Full replacement | Missing fields are reset |
| `PATCH` | Partial update | Document content type and null semantics |
| `DELETE` | Hard delete or documented soft delete | Be explicit about the response behavior |

### use-standard-http-headers
<RuleHeader
  id="use-standard-http-headers"
  level="MUST"
  title="Use Standard HTTP Headers"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/123
Accept: application/json
If-None-Match: "v42"`,
    },
  ]}
/>

- You MUST use standard HTTP headers when your API implements a behavior they cover, and document them in your OpenAPI spec.
- You MUST use `Accept` and `Content-Type` for content negotiation.
- You MUST use `Retry-After` with `429` responses when you can provide meaningful retry guidance.
- You MUST use `ETag` + `If-Match` for optimistic locking (returning `412` on precondition failure).
- You SHOULD consider `ETag` + `If-None-Match` for cache validation (with `304 Not Modified`).
- You MAY use `Prefer` + `Preference-Applied` when clients need to express processing preferences.
- APIs SHOULD support `Accept-Encoding` for response compression (gzip, br) and return `Content-Encoding` when compression is applied. Document whether compression is supported.

### use-http-methods-correctly
<RuleHeader
  id="use-http-methods-correctly"
  level="MUST"
  title="Use HTTP Methods Correctly"
  externalDocs={[{ label: "RFC 9110 — HTTP Semantics", href: "https://www.rfc-editor.org/rfc/rfc9110" }, { label: "RFC 7231 — HTTP/1.1 Semantics and Content (historic)", href: "https://www.rfc-editor.org/rfc/rfc7231" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/{accountId}
GET /accounts?limit=50&offset=0`,
    },
  ]}
/>

Use each method according to its standard semantics as defined in RFC 9110.

#### GET

GET MUST be safe and side-effect free — no mutations, no "mark as viewed" side effects, no triggering background jobs.

- ✅ `GET /accounts/{accountId}`
- ✅ `GET /accounts?limit=50&offset=0`
- ❌ `GET /accounts/{accountId}/disable`
- ❌ `GET /accounts/{accountId}` that updates `lastAccessedAt`

#### POST

- For resource creation, a successful `POST /accounts` MUST return `201 Created` with a `Location` header pointing to the new resource.
- For search operations needing a request body, use `POST /accounts/search` with GET-like semantics — it MUST NOT create a resource and MUST be safe to retry.
- For commands modeling a real-world action, create a request resource: `POST /accounts/{accountId}/disable-requests`.
- ❌ `POST /accounts/{id}` to update (use PATCH or PUT instead)
- ❌ `POST /accounts/{id}/get` (just use GET)

#### PUT

PUT replaces the entire resource representation. Missing fields are reset, not left unchanged. Use PATCH for partial updates.

- ✅ `PUT /accounts/{accountId}` with full representation
- ❌ `PUT /accounts/{accountId}` with only changed fields

#### PATCH

- You MUST document the patch format: a resource-specific patch schema, JSON Merge Patch, or JSON Patch.
- You MUST define null semantics — does sending `null` clear the field, or is it invalid? See [#specify-patch-content-type-and-null-semantics].
- ✅ `PATCH /accounts/{accountId}` with `{ "status": "DISABLED" }`
- ✅ `PATCH /accounts/{accountId}` with JSON Patch ops (if documented)

#### DELETE

DELETE removes a resource or performs a documented soft-delete.

- ✅ `DELETE /accounts/{accountId}` → `204 No Content` for hard delete
- ✅ `DELETE /accounts/{accountId}` → documented soft-delete response (see [#define-soft-delete-behavior])
- ❌ `GET /accounts/{accountId}/delete`

### honor-method-properties
<RuleHeader
  id="honor-method-properties"
  level="MUST"
  title="Honor Method Properties"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/{id}
PUT /accounts/{id}
DELETE /accounts/{id}`,
    },
  ]}
/>

- GET, HEAD, and OPTIONS MUST be safe: repeated calls MUST NOT cause state changes.
- GET, HEAD, PUT, DELETE, and typically PATCH MUST be idempotent: repeating the call has the same effect as a single call.
- GET and HEAD are cacheable: responses can be cached when appropriate.

- ✅ `GET /accounts/{id}` returning current state (safe)
- ❌ `GET /accounts/{id}` that updates `lastViewedAt` (not safe)
- ✅ `DELETE /accounts/{id}` where a repeat returns 404/410 or 204 (idempotent)
- ✅ `PUT /accounts/{id}` full replacement (idempotent)
- ❌ `POST /accounts/{id}/disable` where a repeat creates multiple side effects (not idempotent)
- ✅ `GET /accounts/{id}` cache-validated via `ETag`/`If-None-Match` (see [#use-optimistic-locking-for-concurrent-writes])

Design operations to be idempotent where feasible, especially if clients might retry (see [#prefer-idempotent-post-patch-where-possible], [#support-idempotency-key]). If an operation is genuinely not idempotent, document the retry behavior.

## HTTP Status Codes & Error Handling
### use-standard-http-status-codes
<RuleHeader
  id="use-standard-http-status-codes"
  level="MUST"
  title="Use Standard HTTP Status Codes"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }, { href: "https://www.iana.org/assignments/http-status-codes/http-status-codes.xhtml", label: "IANA HTTP Status Code Registry" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 201 Created
Location: /accounts/123
Content-Type: application/json`,
    },
  ]}
/>

- You MUST use only standard HTTP status codes from RFCs and the IANA registry. Do not invent custom codes or repurpose existing codes.
- Choose the most semantically appropriate code for each condition.

#### Baseline mappings

- `200`: successful request with response body
- `201`: resource created successfully (include `Location` header)
- `202`: request accepted for async processing (see [#support-long-running-operations])
- `204`: successful operation with no response body (DELETE, some PATCHs)
- `301`/`308`: permanent redirects for canonical URL normalization
- `400`: validation errors, malformed requests
- `401`: missing/invalid authentication
- `403`: authenticated but not authorized (when revealing existence is acceptable)
- `404`: resource not found (or "not authorized to know it exists")
- `406`: not acceptable — unsupported `Accept` header (see [#return-406-for-unsupported-accept-headers])
- `409`: conflicts (state transitions, uniqueness constraints)
- `412`: conditional request / optimistic locking failures (ETag/If-Match)
- `429`: rate limiting
- `502`: bad gateway — upstream returned an invalid response
- `503`: service unavailable — temporary overload or maintenance (include `Retry-After`)
- `504`: gateway timeout — upstream did not respond in time
- `5xx`: unexpected server failures

- Prefer `400 Bad Request` for all client input errors. Use `422 Unprocessable Content` only when you need to distinguish syntactically valid but semantically invalid input, and document the distinction per-endpoint.
- Prefer secure defaults — return `404` rather than `403` when resource existence itself is sensitive.
- Be consistent: do not return different codes for the same condition across endpoints.

### define-a-standard-error-contract-in-openapi-problem-details
<RuleHeader
  id="define-a-standard-error-contract-in-openapi-problem-details"
  level="MUST"
  title="Define a Standard Error Contract in OpenAPI (Problem Details)"
  externalDocs={[{ label: "RFC 9457 — Problem Details for HTTP APIs", href: "https://www.rfc-editor.org/rfc/rfc9457" }, { label: "OpenAPI Specification", href: "https://spec.openapis.org/oas/latest.html" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "type": "https://developer.sailpoint.com/problems/validation-error",
  "title": "Validation error",
  "status": 400,
  "detail": "One or more fields are invalid.",
  "instance": "/accounts",
  "errors": [
    { "field": "name", "message": "Must not be blank." }
  ],
  "correlationId": "3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b"
}`,
    },
  ]}
/>

At minimum, every operation should make these things obvious to callers:

- which success responses can happen,
- which error responses can happen,
- what the shared Problem Details shape looks like,
- and what a real error payload looks like.

- Every operation MUST define success responses (status code + schema + examples) and error responses (status code + standardized schema + examples).
- Error responses MUST use Problem Details (RFC 9457) with media type `Content-Type: application/problem+json`.
- For each operation, define the common success responses (2xx) and the expected error responses (400/401/403/404/409/412/429/5xx) where applicable. Use OpenAPI `default` only for truly unexpected server errors.
- Required fields are `type`, `title`, `status`, `detail`, and `instance`.
- Recommended extensions are `errors[]` for field-level validation, `code` for stable application-specific identifiers, and `correlationId` for support and debugging (see [#return-a-request-id-on-every-response]).
- If application-specific error codes are used, they MUST be documented, stable, and MUST NOT replace HTTP status codes.
- Reuse one shared `ProblemDetails` schema across SailPoint APIs so clients can share error handling logic.
- Include at least one accurate error example per operation. Never include secrets or real customer data.
- Register new problem types in the SailPoint problem catalog at [`https://developer.sailpoint.com/problems`](https://developer.sailpoint.com/problems). The `type` URI on every Problem Details response MUST resolve to a catalog entry; do not invent ad-hoc `type` URIs that are not published.
- Examples MUST reflect the published SailPoint error contract where it prescribes field names, extension objects, or `type` URI patterns. The RFC 9457 baseline fields (`type`, `title`, `status`, `detail`, `instance`) plus common extensions (`errors`, `code`, `correlationId`) are the floor — extend or substitute to match the catalog when it differs.

#### Examples

##### Validation error (400)

```json
{
  "type": "https://developer.sailpoint.com/problems/validation-error",
  "title": "Validation error",
  "status": 400,
  "detail": "One or more fields are invalid.",
  "instance": "/accounts",
  "errors": [
    { "field": "name", "message": "Must not be blank." }
  ],
  "correlationId": "3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b"
}
```

##### Optimistic locking failure (412)

```json
{
  "type": "https://developer.sailpoint.com/problems/precondition-failed",
  "title": "Precondition failed",
  "status": 412,
  "detail": "ETag does not match current resource version.",
  "instance": "/accounts/123",
  "code": "ETAG_MISMATCH"
}
```

##### Reusable OpenAPI schema

Declare a single `ProblemDetails` schema in `components/schemas` and reference it from every operation's error responses:

```yaml
components:
  schemas:
    ProblemDetails:
      type: object
      required: [type, title, status]
      properties:
        type:
          type: string
          format: uri
          description: Stable URI identifying the problem type (registered in the SailPoint problem catalog).
        title:
          type: string
          description: Short, human-readable summary of the problem type.
        status:
          type: integer
          minimum: 100
          maximum: 599
          description: HTTP status code.
        detail:
          type: string
          description: Human-readable explanation specific to this occurrence.
        instance:
          type: string
          format: uri
          description: URI reference identifying the specific occurrence.
        code:
          type: string
          description: Stable application-specific error identifier.
        correlationId:
          type: string
          description: Request correlation ID for support and debugging.
        errors:
          type: array
          items: { type: object }
          description: Field-level validation errors.
```

### support-long-running-operations
<RuleHeader
  id="support-long-running-operations"
  level="MUST"
  title="Support Long-Running Operations"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110#section-15.3.3", label: "RFC 9110 §15.3.3 — 202 Accepted" }, { href: "https://google.aip.dev/151", label: "Google AIP-151: Long-Running Operations" }, { href: "https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design#asynchronous-operations", label: "Azure: Asynchronous Operations" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 202 Accepted
Location: /accounts/imports/job-abc-123
Retry-After: 5`,
    },
  ]}
/>

Operations expected to exceed roughly 5 seconds MUST use the async job pattern:

- Return `202 Accepted`.
- Include `Location` and `Retry-After`.
- Expose a status resource with `id`, `status`, timestamps, and `result` or `error`.
- Document how clients poll and what terminal states mean.

1. Client sends the initiating request (typically POST).
2. Server returns `202 Accepted` with a `Location` header pointing to a status resource and a `Retry-After` header.
3. Client polls the status resource.
4. When the job finishes, the status resource includes the result or a link to the result resource.

#### Status resource shape

The status resource MUST include at minimum:

```json
{
  "id": "job-abc-123",
  "status": "IN_PROGRESS",
  "createdAt": "2026-03-05T10:00:00Z",
  "completedAt": null,
  "progress": 42,
  "result": null,
  "error": null
}
```

- `id`: unique job identifier (string)
- `status`: one of `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, or `CANCELLED`
- `createdAt`: creation timestamp (date-time)
- `completedAt`: when the job finished (nullable)
- `progress`: optional completion percentage (0-100)
- `result`: outcome or link to created resource (nullable)
- `error`: Problem Details on failure (nullable, see [#define-a-standard-error-contract-in-openapi-problem-details])

#### Initiation

```http
POST /accounts/imports
Content-Type: application/json

{ "sourceId": "source-123" }
```

```http
HTTP/1.1 202 Accepted
Location: /accounts/imports/job-abc-123
Retry-After: 5
```

#### Polling (in progress)

```http
GET /accounts/imports/job-abc-123
```

```json
{
  "id": "job-abc-123",
  "status": "IN_PROGRESS",
  "createdAt": "2026-03-05T10:00:00Z",
  "completedAt": null,
  "progress": 42
}
```

#### Polling (completed)

```json
{
  "id": "job-abc-123",
  "status": "COMPLETED",
  "createdAt": "2026-03-05T10:00:00Z",
  "completedAt": "2026-03-05T10:05:30Z",
  "progress": 100,
  "result": { "href": "/accounts/imports/job-abc-123/results" }
}
```

#### Polling (failed)

```json
{
  "id": "job-abc-123",
  "status": "FAILED",
  "createdAt": "2026-03-05T10:00:00Z",
  "completedAt": "2026-03-05T10:03:15Z",
  "error": {
    "type": "https://developer.sailpoint.com/problems/import-failed",
    "title": "Import failed",
    "status": 500,
    "detail": "Source connection timed out."
  }
}
```

#### Polling and completion guidance

- Clients MUST respect the `Retry-After` header when present.
- If `Retry-After` is absent, clients SHOULD use exponential backoff starting at 1-2 seconds.
- When the job creates a resource, include a link to that resource in `result`.
- Servers SHOULD retain completed job status for a documented period (at least 24 hours recommended).

Follow the operationId convention: `create<Thing>Job`, `get<Thing>Job`, `list<Thing>Jobs` (see [#provide-a-camelcase-operationid-for-every-operation]).

**Related rules**: [#define-a-standard-error-contract-in-openapi-problem-details] error shape, [#use-429-with-rate-limit-headers] Retry-After, [#prefer-idempotent-post-patch-where-possible] idempotent POST for job creation.

## Idempotency & Retries
### prefer-idempotent-post-patch-where-possible
<RuleHeader
  id="prefer-idempotent-post-patch-where-possible"
  level="SHOULD"
  title="Prefer Idempotent POST/PATCH Where Possible"
  externalDocs={[{ href: "https://stripe.com/docs/idempotency", label: "Stripe API: Idempotency" }]}
  examples={[
    {
      lang: "http",
      code: `POST /accounts
Idempotency-Key: 4d2b8c2d-6dbe-4c5e-9b8f-2d3b5a6c7d8e
Content-Type: application/json

{ "name": "Example" }`,
    },
  ]}
/>

- For operations that clients are likely to retry (network timeouts, 5xx, gateway errors), APIs SHOULD provide an idempotency mechanism for POST and PATCH.
- If duplicate side effects would be harmful, do not rely on clients to "just avoid retries."
- Recommended mechanisms:
  - Optimistic locking for updates (`ETag` + `If-Match`, preferred for PATCH/PUT)
  - `Idempotency-Key` header for side-effecting requests (see [#support-idempotency-key])
  - Secondary/external keys for create operations (see [#use-secondary-keys-for-idempotent-post])
- Prioritize idempotency for:
  - Create endpoints (`POST /resources`) where duplicates are harmful
  - Command endpoints that trigger work (e.g., `POST /imports`, `POST /exports`)
  - PATCH endpoints used by UIs that may retry on transient failures
- When the same request is replayed within the idempotency window, the API SHOULD return the same outcome rather than performing the action twice.
- If a key is reused with a different payload, return `409 Conflict` and explain it.
- The API MUST document retry safety semantics for each endpoint.

### support-idempotency-key
<RuleHeader
  id="support-idempotency-key"
  level="MAY"
  title="Support Idempotency-Key"
  externalDocs={[{ href: "https://stripe.com/docs/idempotency", label: "Stripe API: Idempotency" }]}
  examples={[
    {
      lang: "http",
      code: `POST /accounts
Idempotency-Key: 4d2b8c2d-6dbe-4c5e-9b8f-2d3b5a6c7d8e
Content-Type: application/json

{ "name": "Example" }`,
    },
  ]}
/>

- APIs MAY support the `Idempotency-Key` request header for side-effecting operations (typically POST, sometimes PATCH).
- If supported, you MUST define a clear contract covering:
  - Which endpoints and methods honor the header
  - Key format (UUID v4 recommended)
  - Scope (keys scoped to at minimum the client, endpoint, and method tuple)
  - Uniqueness semantics (reusing a key with a different request payload is an error)
  - Retention window (how long keys are remembered; what happens after expiry)
  - Replay behavior (responses replayed consistently within the retention window)
- If the same key arrives with a matching request, return the recorded response. If the request differs, return `409 Conflict` (or `400`).

```http
POST /accounts
Idempotency-Key: 4d2b8c2d-6dbe-4c5e-9b8f-2d3b5a6c7d8e
Content-Type: application/json

{ "name": "Example" }
```

`Idempotency-Key` does not replace optimistic locking — use `If-Match` for updates to existing resources. Document whether the key is honored on `429`/`5xx` retries.

### use-secondary-keys-for-idempotent-post
<RuleHeader
  id="use-secondary-keys-for-idempotent-post"
  level="MAY"
  title="Use Secondary Keys for Idempotent POST"
  externalDocs={[{ href: "https://stripe.com/docs/idempotency", label: "Stripe API: Idempotency" }]}
  examples={[
    {
      lang: "http",
      code: `POST /accounts
Content-Type: application/json

{ "externalId": "crm:account:12345", "name": "Example" }`,
    },
  ]}
/>

- When creating resources with `POST /collection`, APIs MAY accept a client-provided secondary key (`externalId`, `alternateId`, or `clientToken`) unique within the relevant scope.
- You MUST document the field name, scope, and uniqueness constraints, and enforce uniqueness server-side.
- If the same secondary key is sent with the same payload, return the existing resource (`200 OK` or `201 Created` with the same `Location`).
- If the same secondary key is sent with a conflicting payload, return `409 Conflict` with details.

```http
POST /accounts
Content-Type: application/json

{ "externalId": "crm:account:12345", "name": "Example" }
```

## Caching & Concurrency

### document-caching-behavior
<RuleHeader
  id="document-caching-behavior"
  level="SHOULD"
  title="Document Caching Behavior"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9111", label: "RFC 9111 — HTTP Caching" }, { href: "https://developer.mozilla.org/en-US/docs/Web/HTTP/Caching", label: "MDN: HTTP Caching" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 200 OK
Cache-Control: public, max-age=3600
ETag: "v1-abc123"`,
    },
  ]}
/>

APIs SHOULD document caching behavior per endpoint and use standard HTTP cache headers.

#### When caching is appropriate

Read-only, non-personalized resources (reference data, schema definitions, public configuration):

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=3600
ETag: "v1-abc123"
```

#### When caching is dangerous

Tenant-scoped data, permission-dependent responses, and resources with PII MUST include `Cache-Control: no-store` or `Cache-Control: private, no-cache`:

```http
HTTP/1.1 200 OK
Cache-Control: private, no-cache
ETag: "v42-def456"
```

#### Conditional GETs for cache validation

Return an `ETag` on GET responses and support `If-None-Match`. When the resource hasn't changed, return `304 Not Modified`:

```http
GET /accounts/123
If-None-Match: "v42-def456"
```

```http
HTTP/1.1 304 Not Modified
ETag: "v42-def456"
```

#### Documentation requirements

For each endpoint, document:
- Whether responses are cacheable
- What `Cache-Control` directives are returned
- Whether `ETag`/`If-None-Match` is supported for conditional GETs
- Any CDN or proxy considerations

If caching behavior is not documented, clients SHOULD assume `no-store`.

**Related rules**: [#use-standard-http-headers] standard headers (ETag), [#use-optimistic-locking-for-concurrent-writes] optimistic locking (ETag for writes).

### document-request-and-response-size-limits
<RuleHeader
  id="document-request-and-response-size-limits"
  level="MUST"
  title="Document Request and Response Size Limits"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110#section-15.5.14", label: "RFC 9110 §15.5.14 — 413 Content Too Large" }]}

    },

/>

APIs MUST document request and response size limits for every endpoint or endpoint group that enforces them.

#### Request size limits

- Document the maximum request body size (e.g., "Request bodies must not exceed 1 MB").
- When exceeded, return `413 Content Too Large` with a Problem Details body:

```json
{
  "type": "https://developer.sailpoint.com/problems/content-too-large",

  "status": 413,
  "detail": "Request body exceeds the maximum allowed size of 1048576 bytes.",
  "instance": "/accounts/imports"
```

- List endpoints MUST enforce a maximum page size via the `limit` parameter (see [#support-offset-pagination-for-list-endpoints]) and document the maximum allowed value.

- **Async import/export**: accept a reference to a file and process it asynchronously (see [#support-long-running-operations]).

**Related rules**: [#support-offset-pagination-for-list-endpoints] pagination limits, [#support-long-running-operations] async for large operations, [#define-a-standard-error-contract-in-openapi-problem-details] error response format.

### use-optimistic-locking-for-concurrent-writes
<RuleHeader
  id="use-optimistic-locking-for-concurrent-writes"
  level="SHOULD"
  title="Use Optimistic Locking for Concurrent Writes"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110#section-13.1", label: "RFC 9110 §13.1 — Conditional Requests" }, { href: "https://google.aip.dev/154", label: "Google AIP-154: Resource Freshness" }]}
  examples={[
    {
      lang: "http",
      code: `PATCH /accounts/123
If-Match: "v42"
Content-Type: application/json

{ "name": "Updated Example" }`,
    },
  ]}
/>

Write endpoints for resources modified by multiple actors SHOULD require optimistic locking via `ETag`/`If-Match`.

Use this when silent last-write-wins updates would cause data loss, stale overwrites, or operator confusion.

#### How it works

1. Server returns an `ETag` header on every GET response.
2. Client includes `If-Match: "<etag>"` on PUT, PATCH, or DELETE requests.
3. If the `ETag` matches, the update proceeds and a new `ETag` is returned.
4. If the `ETag` does not match, the server returns `412 Precondition Failed`.

```http
GET /accounts/123
```

```http
HTTP/1.1 200 OK
ETag: "v42"
Content-Type: application/json

{ "id": "123", "name": "Example", "status": "ACTIVE" }
```

```http
PATCH /accounts/123
If-Match: "v42"
Content-Type: application/json

{ "name": "Updated Example" }
```

```http
HTTP/1.1 200 OK
ETag: "v43"
Content-Type: application/json

{ "id": "123", "name": "Updated Example", "status": "ACTIVE" }
```

If another client updated the resource between the GET and the PATCH:

```http
HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json
```

```json
{
  "type": "https://developer.sailpoint.com/problems/precondition-failed",
  "title": "Precondition failed",
  "status": 412,
  "detail": "The resource has been modified since your last read. Re-fetch and retry.",
  "instance": "/accounts/123",
  "code": "ETAG_MISMATCH"
}
```

#### When to require it

- Resources with multiple writers (users, services, concurrent automations)
- Configuration-style resources where silent overwrites cause operational harm
- Resources where PATCH/PUT is used in read-modify-write workflows
- For single-writer resources where last-write-wins is acceptable, optimistic locking MAY be omitted — but document the concurrency semantics either way.

#### Implementation notes

- Use opaque, strong ETags (not weak ETags) for write concurrency.
- The ETag value can be a hash, version counter, or timestamp — as long as it changes on every write.
- If `If-Match` is required but missing, return `428 Precondition Required`.
- Define the conflict response and error schema in OpenAPI; document the concurrency contract on the write operation.

Declare the precondition in OpenAPI so generators and clients pick it up automatically:

```yaml
paths:
  /accounts/{id}:
    get:
      responses:
        "200":
          description: OK
          headers:
            ETag:
              description: Version identifier for optimistic locking.
              schema: { type: string }
    patch:
      parameters:
        - in: header
          name: If-Match
          description: Provide the ETag from the last read to prevent lost updates.
          required: true
          schema: { type: string }
```

#### Date-based alternative: Last-Modified + If-Unmodified-Since

When you already track a reliable `updatedAt` timestamp and want a simpler header pair, return `Last-Modified` on reads and require `If-Unmodified-Since` on writes. If the resource changed since that date, respond with `412 Precondition Failed`. This is a valid fallback but is coarser than ETags — two writes within the same second can both pass the check.

#### Avoid embedding ETags/version in business objects

Embedding an `etag` or `version` field inside the resource body (rather than in the HTTP header) can be convenient for bulk or search responses, but it mixes HTTP concerns into your domain object. If you do it, mark the field read-only, document the semantics clearly, and keep the authoritative version in the `ETag` header.

**Related rules**: [#use-standard-http-headers] standard headers, [#use-standard-http-status-codes] status codes (412), [#define-a-standard-error-contract-in-openapi-problem-details] error format, [#document-caching-behavior] caching (ETag for reads).

## Retry Semantics

### classify-error-retryability
<RuleHeader
  id="classify-error-retryability"
  level="MUST"
  title="Classify Error Retryability"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc9110", label: "RFC 9110 — HTTP Semantics" }, { href: "https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/", label: "AWS Builders' Library: Timeouts, Retries, and Backoff" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "type": "https://developer.sailpoint.com/problems/source-connection-timeout",
  "title": "Source connection timeout",
  "status": 503,
  "detail": "Could not connect to the configured source.",
  "retryable": true
}`,
    },
  ]}
/>

APIs MUST classify error responses into retryable and non-retryable categories, and document retry expectations for any application-specific error codes.

At minimum, tell callers:

- which errors they can retry as-is,
- which ones require fixing the request first,
- and whether any custom error code changes the default retry behavior.

#### Retryable errors

| Status | Meaning | Retry guidance |
|---|---|---|
| `429` | Too Many Requests | Retry after `Retry-After` header value (see [#use-429-with-rate-limit-headers]) |
| `502` | Bad Gateway | Retry with exponential backoff |
| `503` | Service Unavailable | Retry after `Retry-After` if present, else exponential backoff |
| `504` | Gateway Timeout | Retry with exponential backoff |

For all retryable errors, the server SHOULD include a `Retry-After` header when it can estimate recovery time.

#### Non-retryable errors

| Status | Meaning | Why not retryable |
|---|---|---|
| `400` | Bad Request | Fix the request payload |
| `401` | Unauthorized | Obtain valid credentials |
| `403` | Forbidden | Insufficient permissions — retrying won't help |
| `404` | Not Found | Resource does not exist |
| `405` | Method Not Allowed | Wrong HTTP method |
| `406` | Not Acceptable | Unsupported Accept header (see [#return-406-for-unsupported-accept-headers]) |
| `409` | Conflict | Resolve the conflict, then retry with corrected state |
| `410` | Gone | Resource permanently removed |
| `412` | Precondition Failed | Re-fetch resource, then retry with updated ETag |
| `413` | Content Too Large | Reduce payload size |
| `422` | Unprocessable Content | Fix semantic errors in the request |

Note: `409` and `412` are "retry after corrective action" — the client can retry, but must change the request first.

#### Ambiguous: 500 Internal Server Error

`500` errors MAY be transient or permanent. Clients SHOULD retry `500` at most once with a short delay. If the retry also returns `500`, stop and report the error.

#### Application-specific error codes

- If your API defines application-specific error codes (see [#define-a-standard-error-contract-in-openapi-problem-details]), each code MUST document whether the error is retryable.
- Consider adding a `retryable` boolean extension to Problem Details responses:

```json
{
  "type": "https://developer.sailpoint.com/problems/source-connection-timeout",
  "title": "Source connection timeout",
  "status": 503,
  "detail": "Could not connect to the configured source.",
  "retryable": true
}
```

#### Client implementation guidance

- SHOULD use exponential backoff with jitter.
- MUST respect `Retry-After` headers when present — the server value overrides the client's calculated delay.
- SHOULD cap the maximum retry count (3–5 retries is typical) and the maximum per-attempt delay.
- SHOULD log every retry attempt with the status code and attempt number.

Reference backoff algorithm:

```
base_delay = 1 second
max_delay  = 30 seconds
max_retries = 4

for attempt in 1..max_retries:
    delay = min(base_delay * 2^(attempt - 1), max_delay)
    jitter = random(0, delay)            # full jitter
    sleep(jitter)
    response = make_request()
    if response.status not in [429, 500, 502, 503, 504]:
        break
    if response.headers["Retry-After"]:
        sleep(parse_retry_after(response.headers["Retry-After"]))
```

Use **full jitter** (`random(0, delay)`) rather than no jitter — synchronized retries produce thundering-herd outages.

**Related rules**: [#use-standard-http-status-codes] status codes, [#define-a-standard-error-contract-in-openapi-problem-details] error format, [#use-429-with-rate-limit-headers] rate limit headers, [#prefer-idempotent-post-patch-where-possible] idempotent retries.
