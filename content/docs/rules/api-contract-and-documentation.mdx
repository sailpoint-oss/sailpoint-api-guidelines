These rules explain how to specify, document, and publish APIs. The goal is clear, consistent
contracts and docs that customers and partners can actually use.

## API Design & Documentation

### #100 - Follow API-First
<RuleHeader id="100" level="SHOULD" title="Follow API-First" externalDocs={[{ href: "https://www.postman.com/api-first/", label: "Postman API-first" }, { href: "https://swagger.io/resources/articles/adopting-an-api-first-approach/", label: "Swagger: API Design-First" }]} />

- Teams SHOULD draft the OpenAPI spec early — paths, schemas, errors, auth, pagination, filtering — and review it with stakeholders before writing production code.
- The spec and code SHOULD stay in lockstep in version control, with the spec treated as a first-class artifact.
- Use contract tests or spec validation in CI so changes are visible and reviewable.
- Every operation SHOULD have `summary`, `description`, `operationId`, tags, request/response schemas, error responses, security requirements, and examples for key request/response bodies.
- Backward-compatibility SHOULD be evaluated for changes within the same major version.

### #101 - Provide an OpenAPI Specification
<RuleHeader id="101" level="MUST" title="Provide an OpenAPI Specification" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- Every API MUST have an OpenAPI Specification, stored in version control alongside the service code and published for consumers.
- The OpenAPI document MUST be validated in CI so invalid specs cannot be released.
- Use a changelog or release notes that reference spec changes, and keep examples accurate — no secrets or real customer data.
- Prefer OpenAPI 3.0.3 for maximum tooling compatibility. OpenAPI 3.1.x is allowed when JSON Schema features (e.g., `type` arrays for nullable) are needed.

For documentation quality levels (Level 1/Level 2 requirements), see [#902].

### #102 - Provide an API User Manual
<RuleHeader id="102" level="SHOULD" title="Provide an API User Manual" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]} />

Teams SHOULD provide an API user manual that complements the OpenAPI spec, covering at minimum:

- **Getting started** — authentication approach, base URLs/environments, common headers.
- **Core workflows** — step-by-step guides per use case (create, update, search, pagination).
- **Edge cases** — validation rules, idempotency expectations, conflict handling, eventual consistency.
- **Error handling** — common errors and recommended client behavior for retry vs no-retry.
- **Performance** — pagination guidance, filtering/sorting limitations, rate limits (see [#307]), expected latency, recommended client timeout values.

Link the manual from OpenAPI using `externalDocs` (root-level and/or per-tag/per-operation). Include at least one end-to-end example per primary workflow.

## Text Formatting & Naming Conventions
### #103 - Write in U.S. English
<RuleHeader id="103" level="MUST" title="Write in U.S. English" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- All API-surface text MUST use U.S. English spelling and conventions. This applies to:
  - OpenAPI descriptions, summaries, tags, and schema documentation.
  - Error `title`/`detail` text and any human-readable messages.
  - Developer documentation (guides, rule pages).
- This rule does not require clients to send U.S. English values unless a field is explicitly documented as English text.
- Prefer consistent terminology across endpoints — avoid synonyms for the same concept. Expand acronyms once when first introduced.

SailPoint APIs do not currently support content localization via `Accept-Language`. For internationalization-related data formats, see [#803].

### #104 - Use camelCase for JSON Properties
<RuleHeader id="104" level="MUST" title="Use camelCase for JSON Properties" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- JSON property names MUST use camelCase for request and response bodies.
- For path segments and path parameters, see [#107]. For query parameters, see [#108]. For ASCII requirements, see [#105].

- ✅ `createdAt`, `identityProfileId`, `lastLogin`
- ❌ `created_at` (snake_case)
- ❌ `CreatedAt` (PascalCase)
- ❌ `created-at` (kebab-case)

#### Acronyms

Prefer `oauthClientId` over `OAuthClientID`. Be consistent across the entire API surface.

### #105 - Use ASCII for API Identifiers
<RuleHeader id="105" level="MUST" title="Use ASCII for API Identifiers" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- All API identifiers MUST use ASCII characters only. This applies to:
  - URL path segments (resource names).
  - Path parameter names (`{identityId}`).
  - Query parameter names (`?sortOrder=asc`).
  - JSON property names (`createdAt`).
  - Enum tokens when they represent identifiers (`"PENDING_APPROVAL"`).
  - Header names in documentation/examples.
- This does not apply to free-form human text fields (e.g., `displayName`, `description`) where UTF-8 is expected.

- ✅ `identityProfileId`
- ✅ `createdAt`
- ❌ `créatedAt`
- ❌ `名前`

### #106 - Pluralize Array Property Names
<RuleHeader id="106" level="SHOULD" title="Pluralize Array Property Names" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Array properties SHOULD use plural names to signal multiple values.
- If a plural name is awkward or ambiguous, choose a clear collective noun and document it. Be consistent across endpoints.

- ✅ `items`, `accounts`, `entitlements`, `roles`
- ✅ `children` (already plural)
- ✅ `data` / `metadata` (acceptable common exceptions; use consistently)
- ❌ `item` for an array
- ❌ `account` for an array

### #107 - Use Lowercase Hyphenated Path Segments and camelCase Path Parameters
<RuleHeader id="107" level="MUST" title="Use Lowercase Hyphenated Path Segments and camelCase Path Parameters" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Path segments MUST use lowercase with hyphens (e.g., `/user-profiles`).
- Path parameters MUST use camelCase (e.g., `{userId}`).

- ✅ `/identity-profiles/{identityProfileId}`
- ✅ `/access-requests/{accessRequestId}`
- ❌ `/IdentityProfiles/{IdentityProfileId}` (wrong casing)
- ❌ `/identity_profiles/{identity_profile_id}` (snake_case)

### #108 - Use camelCase for Query Parameters
<RuleHeader id="108" level="MUST" title="Use camelCase for Query Parameters" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Query parameter names MUST use camelCase.
- Prefer conventional query parameter names for pagination, filtering, and sorting (see [#600]). Be consistent across endpoints.

- ✅ `?sortOrder=asc&maxResults=50`
- ✅ `?includeDisabled=true`
- ✅ `?createdAfter=2026-01-01T00:00:00Z`

- ❌ `?sort_order=asc` (snake_case)
- ❌ `?SortOrder=asc` (PascalCase)
- ❌ `?include-disabled=true` (kebab-case)

### #109 - Use Upper-Case Words with Hyphens
<RuleHeader id="109" level="SHOULD" title="Use Upper-Case Words with Hyphens" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- When documenting HTTP header names (including custom headers), teams SHOULD use the conventional Upper-Case-Words-With-Hyphens style.
- Prefer standardized headers over custom ones where possible (see [#400]).

- ✅ `Content-Type`, `If-Match`, `If-None-Match`, `Retry-After`
- ✅ `X-Request-Id` (if using an `X-` prefixed header during a migration)
- ❌ `content-type`
- ❌ `IF_MATCH`

### #110 - Pluralize Collection Resource Names
<RuleHeader id="110" level="MUST" title="Pluralize Collection Resource Names" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Collection endpoints MUST use plural resource names.
- Use domain language and stable nouns (see [#506]). If a term is uncountable (rare), pick a consistent convention and document it.

- ✅ `GET /accounts` (collection)
- ✅ `GET /accounts/{accountId}` (single resource)
- ✅ `GET /identity-profiles` / `GET /identity-profiles/{identityProfileId}`
- ❌ `GET /account` (ambiguous)
- ❌ `GET /Accounts` (wrong casing)

### #111 - Follow Naming Convention for Permissions (Scopes)
<RuleHeader id="111" level="MUST" title="Follow Naming Convention for Permissions (Scopes)" externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc6749", label: "RFC 6749 — OAuth 2.0" }]} />

Scopes MUST follow the canonical format:

```text
<domain>:<resource>:<action>
```

- `<domain>` — stable product/domain namespace (lowercase, ASCII).
- `<resource>` — plural resource family (lowercase, ASCII).
- `<action>` — one of: `read`, `write`, `admin`.
  - `read` — read-only access (GET, and "search semantics" endpoints).
  - `write` — create/update/delete access (POST/PATCH/PUT/DELETE).
  - `admin` — elevated/tenant-admin operations.
- Additional verbs MUST be standardized for the domain and documented. Do not invent ad-hoc verbs per endpoint.

#### Examples

- `identity:accounts:read`
- `identity:accounts:write`
- `identity:accounts:admin`
- `identity:entitlements:read`

#### Endpoint documentation

- OpenAPI `security` requirements MUST list the full set of scopes accepted for the operation (see [#300]/[#206]).
- If an endpoint supports multiple privilege modes, document them explicitly.

#### Anti-examples

- `Identity.Accounts.Read` (wrong separators/case)
- `accounts:read` (missing domain)
- `identity:readAccounts` (inconsistent action encoding)

### #112 - Declare Enum Values in UPPER_SNAKE_CASE Strings
<RuleHeader id="112" level="MUST" title="Declare Enum Values in UPPER_SNAKE_CASE Strings" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Enum values MUST be expressed as UPPER_SNAKE_CASE strings.
- Enum tokens are part of the public contract. Do not rename existing enum values without a compatibility/migration plan.

- ✅ `"ACTIVE"`
- ✅ `"PENDING_APPROVAL"`
- ❌ `"active"` (wrong case)
- ❌ `"PendingApproval"` (camel/Pascal case)
- ❌ `"Pending Approval"` (spaces)

```yaml
status:
  type: string
  enum: [ACTIVE, PENDING_APPROVAL, DISABLED]
```

## Specification Guidelines
### #113 - Follow SailPoint API Guidelines
<RuleHeader id="113" level="MUST" title="Follow SailPoint API Guidelines" externalDocs={[{ href: "https://opensource.zalando.com/restful-api-guidelines/", label: "Zalando RESTful API Guidelines" }]} />

- APIs MUST follow these guidelines. Treat the OpenAPI spec as the contract and review guideline compliance as part of API review.
- Use automated checks where possible — linting, OpenAPI validation, compatibility checks, contract tests.
- Any deliberate exception MUST be documented with rationale (and a remediation plan where applicable) using the review ledger.

### #114 - Provide a Detailed API Description
<RuleHeader id="114" level="MUST" title="Provide a Detailed API Description" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

APIs MUST provide a detailed description covering what the API does and how consumers should use it. At minimum include:

- Purpose and scope (in-scope vs out-of-scope).
- Intended audience (internal vs external) and required licensing/entitlements (see [#115]).
- Authentication model and high-level authorization expectations (see [#300], [#206]).
- Primary workflows and "happy path" usage (link to guides/user manual; see [#102]).
- Major edge cases affecting client correctness: pagination defaults, filtering/sorting constraints, idempotency/retry guidance, consistency expectations.
- Versioning/deprecation model and how changes are communicated (see [#208], [#209]).

Put this in OpenAPI `info.description` and/or tag-level descriptions, and link to deeper guides via `externalDocs`. A reviewer should be able to answer: what is this API for, who can use it, and how do I perform the primary workflows?

### #115 - Describe Every Parameter and Property
<RuleHeader id="115" level="MUST" title="Describe Every Parameter and Property" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

Every query parameter, path parameter, request property, and response property MUST have a clear description covering (as applicable):

- Meaning/semantics — what it represents, not just its data type.
- Constraints — allowed values, ranges, patterns, maximum lengths.
- Default behavior when omitted (see [#709]).
- Null/omission behavior where relevant (see [#700]).
- Security/privacy implications (e.g., whether values are tenant-scoped, PII).

Empty descriptions are not acceptable. Neither are descriptions that restate the property name (e.g., "The status.").

### #116 - Provide Examples for Every Parameter and Property
<RuleHeader id="116" level="MUST" title="Provide Examples for Every Parameter and Property" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- Every query parameter, path parameter, request property, and response property MUST include at least one accurate example.
- Examples MUST conform to the declared schema and formats.
- Prefer OpenAPI `example`/`examples` so tooling can render them.
- Provide examples for both success and error responses (see [#404]).
- Never include secrets or real customer data.

### #117 - Keep Operation Summaries to 5 Words or Fewer
<RuleHeader id="117" level="SHOULD" title="Keep Operation Summaries to 5 Words or Fewer" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- Operation `summary` fields SHOULD be five words or fewer. Put details in `description`.
- Prefer action-oriented summaries aligned with the HTTP method.

- ✅ `List accounts`
- ✅ `Get account`
- ❌ `Get accounts for a given identity profile and include nested entitlements` (too long; belongs in `description`)

### #118 - Avoid Qualifying Verbs
<RuleHeader id="118" level="SHOULD" title="Avoid Qualifying Verbs" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Boolean fields and other descriptive properties SHOULD avoid qualifying verbs like `is`, `has`, `can` when the adjective alone is clear.
- Exception: use a verb when the adjective is genuinely ambiguous (e.g., `canDelete` may be clearer than `deletable`).

- ✅ `enabled` over `isEnabled`
- ✅ `active` over `isActive`
- ✅ `visible` over `isVisible`

### #119 - Use Positive Semantics for Boolean Fields
<RuleHeader id="119" level="SHOULD" title="Use Positive Semantics for Boolean Fields" externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]} />

- Boolean properties SHOULD use positive semantics.
- If an API already has a negative boolean (`disabled`), do not add a second inverted boolean (`enabled`). Keep one field and document it clearly.

- ✅ `enabled` over `disabled`
- ✅ `included` over `excluded`
- ✅ `verified` over `unverified`

## Operation & Parameter Documentation
### #120 - Describe the Filters Parameter (Standard Format)
<RuleHeader id="120" level="MUST" title="Describe the Filters Parameter (Standard Format)" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]} />

When an endpoint supports the `filters` parameter, APIs MUST use the prescribed description template below. Customize the supported-field list per endpoint, but keep the structure consistent.

```text
Filters results using the standard expression language.

Syntax:
  filters=<expr>

Operators:
  eq, ne, lt, lte, gt, gte, co (contains), sw (startsWith), ew (endsWith),
  in (set membership), pr (present)

Grouping:
  Use parentheses for grouping and AND/OR for boolean composition.

Supported fields:
  - fieldA (string)
  - fieldB (enum: ...)
  - created (date-time)

Examples:
  filters=status eq "ACTIVE"
  filters=(status eq "ACTIVE" or status eq "PENDING") and createdAt gt "2025-01-01T00:00:00Z"
```

- Each endpoint MUST document the supported field whitelist and include at least one filter example.

**Related**: shared query story in [#604] and implicit/default behavior guidance in [#603].

### #121 - Describe the Sorters Parameter (Standard Format)
<RuleHeader id="121" level="MUST" title="Describe the Sorters Parameter (Standard Format)" externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]} />

When an endpoint supports the `sorters` parameter, APIs MUST use the prescribed description template below. Customize the supported-field list per endpoint.

```text
Sorts results by one or more fields.

Syntax:
  sorters=<field>:<direction>[,<field>:<direction>...]

Direction:
  asc | desc

Supported fields:
  - name
  - createdAt
  - status

Default ordering:
  If sorters is omitted, results are ordered by <defaultSortPolicy>.

Examples:
  sorters=name:asc
  sorters=status:asc,created:desc
```

- Sort fields MUST be documented, and the API MUST guarantee a stable ordering for pagination.

**Related**: shared query story in [#604] and default ordering policy in [#603].

### #122 - Provide a camelCase operationId for Every Operation
<RuleHeader id="122" level="MUST" title="Provide a camelCase operationId for Every Operation" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- Every operation MUST define a unique `operationId` in camelCase, unique across the entire spec (including across tags).
- These values are part of the public contract for tooling and SDKs. Do not rename `operationId` values without a compatibility plan.

#### Recommended patterns

- GET collection: `list<ResourcePlural>`
- GET item: `get<Resource>`
- POST collection: `create<Resource>`
- PUT/PATCH: `update<Resource>`
- DELETE: `delete<Resource>`
- POST search endpoints (see [#604]): `search<ResourcePlural>`
- Long-running jobs/resources: `create<Thing>Job` (POST), `get<Thing>Job` (GET), `list<Thing>Jobs` (GET)

| Method | Path | operationId |
| --- | --- | --- |
| GET | `/accounts` | `listAccounts` |
| GET | `/accounts/{id}` | `getAccount` |
| POST | `/accounts` | `createAccount` |
| POST | `/accounts/search` | `searchAccounts` |
| PATCH | `/accounts/{id}` | `updateAccount` |
| DELETE | `/accounts/{id}` | `deleteAccount` |

### #123 - Provide a Tag for Every Operation
<RuleHeader id="123" level="MUST" title="Provide a Tag for Every Operation" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

- Each operation MUST be assigned exactly one tag that exists in the root spec's `tags` array.
- Prefer resource-centric tags (e.g., `Accounts`, `Entitlements`).
- Keep tags stable across versions. Tag descriptions SHOULD explain what belongs in the tag.

### #124 - Provide x-sailpoint-resource-operation-id for Path Parameters
<RuleHeader id="124" level="MUST" title="Provide x-sailpoint-resource-operation-id for Path Parameters" externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]} />

SailPoint tooling maps path parameters back to the operation that provides valid values for them.

- For path parameters (except enums and user-defined values), APIs MUST provide a camelCase operation identifier under `x-sailpoint-resource-operation-id` on the path parameter definition.
- The value MUST be camelCase and SHOULD align with the operation's `operationId` (see [#122]).
- Do not change these identifiers without a compatibility plan — tooling depends on them.

```yaml
paths:
  /accounts/{accountId}:
    get:
      operationId: getAccount
      parameters:
        - name: accountId
          in: path
          required: true
          schema:
            type: string
          x-sailpoint-resource-operation-id: getAccount
```
