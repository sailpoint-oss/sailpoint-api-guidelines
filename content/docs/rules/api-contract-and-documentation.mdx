choices keep an API easy to consume.

- Which naming and example conventions should be used everywhere?

## API Design & Documentation

### follow-api-first
<RuleHeader
  id="follow-api-first"
  level="SHOULD"
  title="Follow API-First"
  externalDocs={[{ href: "https://www.postman.com/api-first/", label: "Postman API-first" }, { href: "https://swagger.io/resources/articles/adopting-an-api-first-approach/", label: "Swagger: API Design-First" }]}
  examples={[
    {
      lang: "yaml",
      code: `openapi: 3.0.3
info:
  title: Accounts API
  version: "2026-04"
paths:
  /accounts: { get: { operationId: listAccounts } }`,
    },
  ]}
/>

- Teams SHOULD draft and review the OpenAPI contract before or alongside implementation.
- Review paths, schemas, auth, errors, pagination, filtering, and primary examples before production code is finalized.
- Keep the spec in version control next to the service code and validate it in CI.
- Check backward compatibility for changes within the same major version.

### provide-an-openapi-specification
<RuleHeader
  id="provide-an-openapi-specification"
  level="MUST"
  title="Provide an OpenAPI Specification"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `openapi: 3.0.3
info:
  title: Accounts API
  version: "2026-04"
  description: Manage identity accounts.`,
    },
  ]}
/>

- Every API MUST publish an OpenAPI specification stored in version control next to the service code.
- The spec MUST be validated in CI so invalid contracts cannot be released.
- Keep examples accurate and sanitized. Never publish secrets or real customer data.
- Prefer OpenAPI 3.0.3 for broad tooling compatibility. Use OpenAPI 3.1.x when its JSON Schema features are required.

For documentation quality levels (Level 1/Level 2 requirements), see [#publish-an-openapi-specification-meet-doc-quality-levels].

### provide-an-api-user-manual
<RuleHeader
  id="provide-an-api-user-manual"
  level="SHOULD"
  title="Provide an API User Manual"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "yaml",
      code: `info:
  title: Accounts API
  description: See the user manual for workflows and edge cases.
externalDocs:
  url: https://developer.sailpoint.com/docs/accounts
  description: Accounts API user manual`,
    },
  ]}
/>

If a new consumer cannot succeed from OpenAPI alone, teams SHOULD provide a short user manual that covers:

- **Getting started** — authentication approach, base URLs/environments, common headers.
- **Core workflows** — step-by-step guides per use case (create, update, search, pagination).
- **Edge cases** — validation rules, idempotency expectations, conflict handling, eventual consistency.
- **Error handling** — common errors and recommended client behavior for retry vs no-retry.
- **Performance** — pagination guidance, filtering/sorting limitations, rate limits (see [#document-and-enforce-rate-limits]), expected latency, recommended client timeout values.

Link the manual from OpenAPI using `externalDocs`. Include at least one end-to-end example for each primary workflow.

## Text Formatting & Naming Conventions

If you only need the naming defaults, use this shortcut:

- JSON properties and query parameters: camelCase
- Path segments: lowercase-hyphenated
- Path parameters: camelCase
- Enum values: UPPER_SNAKE_CASE

### write-in-u-s-english
<RuleHeader
  id="write-in-u-s-english"
  level="MUST"
  title="Write in U.S. English"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "yaml",
      code: `summary: List authorized accounts
description: Returns the color-coded status for each account.`,
    },
  ]}
/>

- All API-surface text MUST use U.S. English spelling and conventions. This applies to:
  - OpenAPI descriptions, summaries, tags, and schema documentation.
  - Error `title`/`detail` text and any human-readable messages.
  - Developer documentation (guides, rule pages).
- This rule does not require clients to send U.S. English values unless a field is explicitly documented as English text.
- Prefer consistent terminology across endpoints — avoid synonyms for the same concept. Expand acronyms once when first introduced.

SailPoint APIs do not currently support content localization via `Accept-Language`. For internationalization-related data formats, see [#use-standard-country-language-and-currency-codes].

### use-camelcase-for-json-properties
<RuleHeader
  id="use-camelcase-for-json-properties"
  level="MUST"
  title="Use camelCase for JSON Properties"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "createdAt": "2026-01-15T10:00:00Z",
  "identityProfileId": "abc-123",
  "lastLogin": "2026-04-22T08:00:00Z"
}`,
    },
  ]}
/>

- JSON property names MUST use camelCase for request and response bodies.
- For path segments and path parameters, see [#use-lowercase-hyphenated-path-segments-and-camelcase-path-parameters]. For query parameters, see [#use-camelcase-for-query-parameters]. For ASCII requirements, see [#use-ascii-for-api-identifiers].

- ✅ `createdAt`, `identityProfileId`, `lastLogin`
- ❌ `created_at` (snake_case)
- ❌ `CreatedAt` (PascalCase)
- ❌ `created-at` (kebab-case)

#### Acronyms

Prefer `oauthClientId` over `OAuthClientID`. Be consistent across the entire API surface.

### use-ascii-for-api-identifiers
<RuleHeader
  id="use-ascii-for-api-identifiers"
  level="MUST"
  title="Use ASCII for API Identifiers"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "identityProfileId": "abc-123",
  "createdAt": "2026-01-15T10:00:00Z"
}`,
    },
  ]}
/>

- All API identifiers MUST use ASCII characters only. This applies to:
  - URL path segments (resource names).
  - Path parameter names (`{identityId}`).
  - Query parameter names (`?sortOrder=asc`).
  - JSON property names (`createdAt`).
  - Enum tokens when they represent identifiers (`"PENDING_APPROVAL"`).
  - Header names in documentation/examples.
- This does not apply to free-form human text fields (e.g., `displayName`, `description`) where UTF-8 is expected.

- ✅ `identityProfileId`
- ✅ `createdAt`
- ❌ `créatedAt`
- ❌ `名前`

### pluralize-array-property-names
<RuleHeader
  id="pluralize-array-property-names"
  level="SHOULD"
  title="Pluralize Array Property Names"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "accounts": [
    { "id": "a1" },
    { "id": "a2" }
  ]
}`,
    },
  ]}
/>

- Array properties SHOULD use plural names to signal multiple values.
- If a plural name is awkward or ambiguous, choose a clear collective noun and document it. Be consistent across endpoints.

- ✅ `items`, `accounts`, `entitlements`, `roles`
- ✅ `children` (already plural)
- ✅ `data` / `metadata` (acceptable common exceptions; use consistently)
- ❌ `item` for an array
- ❌ `account` for an array

### use-lowercase-hyphenated-path-segments-and-camelcase-path-parameters
<RuleHeader
  id="use-lowercase-hyphenated-path-segments-and-camelcase-path-parameters"
  level="MUST"
  title="Use Lowercase Hyphenated Path Segments and camelCase Path Parameters"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /identity-profiles/{identityProfileId}
GET /access-requests/{accessRequestId}`,
    },
  ]}
/>

- Path segments MUST use lowercase with hyphens (e.g., `/user-profiles`).
- Path parameters MUST use camelCase (e.g., `{userId}`).

- ✅ `/identity-profiles/{identityProfileId}`
- ✅ `/access-requests/{accessRequestId}`
- ❌ `/IdentityProfiles/{IdentityProfileId}` (wrong casing)
- ❌ `/identity_profiles/{identity_profile_id}` (snake_case)

### use-camelcase-for-query-parameters
<RuleHeader
  id="use-camelcase-for-query-parameters"
  level="MUST"
  title="Use camelCase for Query Parameters"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?sortOrder=asc&includeDisabled=true&createdAfter=2026-01-01T00:00:00Z`,
    },
  ]}
/>

- Query parameter names MUST use camelCase.
- Prefer conventional query parameter names for pagination, filtering, and sorting (see [#use-conventional-query-parameters]). Be consistent across endpoints.

- ✅ `?sortOrder=asc&includeDisabled=true`
- ✅ `?includeDisabled=true`
- ✅ `?createdAfter=2026-01-01T00:00:00Z`

- ❌ `?sort_order=asc` (snake_case)
- ❌ `?SortOrder=asc` (PascalCase)
- ❌ `?include-disabled=true` (kebab-case)

### use-upper-case-words-with-hyphens
<RuleHeader
  id="use-upper-case-words-with-hyphens"
  level="SHOULD"
  title="Use Upper-Case Words with Hyphens"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `Content-Type: application/json
If-Match: "v42"
Retry-After: 30`,
    },
  ]}
/>

- When documenting HTTP header names (including custom headers), teams SHOULD use the conventional Upper-Case-Words-With-Hyphens style.
- Prefer standardized headers over custom ones where possible (see [#use-standard-http-headers]).

- ✅ `Content-Type`, `If-Match`, `If-None-Match`, `Retry-After`
- ✅ `X-Request-Id` (if using an `X-` prefixed header during a migration)
- ❌ `content-type`
- ❌ `IF_MATCH`

### pluralize-collection-resource-names
<RuleHeader
  id="pluralize-collection-resource-names"
  level="MUST"
  title="Pluralize Collection Resource Names"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts
GET /accounts/{accountId}
GET /identity-profiles/{identityProfileId}`,
    },
  ]}
/>

- Collection endpoints MUST use plural resource names.
- Use domain language and stable nouns (see [#use-domain-specific-resource-names]). If a term is uncountable (rare), pick a consistent convention and document it.

- ✅ `GET /accounts` (collection)
- ✅ `GET /accounts/{accountId}` (single resource)
- ✅ `GET /identity-profiles` / `GET /identity-profiles/{identityProfileId}`
- ❌ `GET /account` (ambiguous)
- ❌ `GET /Accounts` (wrong casing)

### follow-naming-convention-for-permissions-scopes
<RuleHeader
  id="follow-naming-convention-for-permissions-scopes"
  level="MUST"
  title="Follow Naming Convention for Permissions (Scopes)"
  externalDocs={[{ href: "https://www.rfc-editor.org/rfc/rfc6749", label: "RFC 6749 — OAuth 2.0" }]}
  examples={[
    {
      lang: "text",
      code: `idn:accounts:read
idn:accounts:write
cam:feature:read`,
    },
  ]}
/>

Scopes MUST follow the canonical format:

```text
<domain>:<resource>:<action>
```

- `<domain>` — stable product/domain namespace (lowercase, ASCII).
- `<resource>` — plural resource family (lowercase, ASCII).
- `<action>` — one of: `read`, `write`, `admin`.
  - `read` — read-only access (GET, and "search semantics" endpoints).
  - `write` — create/update/delete access (POST/PATCH/PUT/DELETE).
  - `admin` — elevated/tenant-admin operations.
- Additional verbs MUST be standardized for the domain and documented. Do not invent ad-hoc verbs per endpoint.

#### Examples

Use real product namespaces and scope families (not a generic `identity` placeholder):

- `idn:transform:read`
- `cam:feature:read`
- `das:feature:manage`
- `idn:accounts:read`
- `idn:accounts:write`

#### Endpoint documentation

- OpenAPI `security` requirements MUST list the full set of scopes accepted for the operation (see [#secure-endpoints-with-oauth-2-0] and [#define-and-assign-scopes]).
- If an endpoint supports multiple privilege modes, document them explicitly.

#### Anti-examples

- `Identity.Accounts.Read` (wrong separators/case)
- `accounts:read` (missing domain)
- `idn:readAccounts` (inconsistent action encoding — use `idn:accounts:read`)

### declare-enum-values-in-upper-snake-case-strings
<RuleHeader
  id="declare-enum-values-in-upper-snake-case-strings"
  level="MUST"
  title="Declare Enum Values in UPPER_SNAKE_CASE Strings"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "yaml",
      code: `status:
  type: string
  enum: [ACTIVE, PENDING_APPROVAL, DISABLED]`,
    },
  ]}
/>

- Enum values MUST be expressed as UPPER_SNAKE_CASE strings.
- Enum tokens are part of the public contract. Do not rename existing enum values without a compatibility/migration plan.

- ✅ `"ACTIVE"`
- ✅ `"PENDING_APPROVAL"`
- ❌ `"active"` (wrong case)
- ❌ `"PendingApproval"` (camel/Pascal case)
- ❌ `"Pending Approval"` (spaces)

### provide-a-detailed-api-description
<RuleHeader
  id="provide-a-detailed-api-description"
  level="MUST"
  title="Provide a Detailed API Description"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `info:
  title: Accounts API
  description: |
    Manages identity accounts. Audience: tenant admins.
    See externalDocs for workflows, pagination, and versioning policy.

    },
  ]}
/>

APIs MUST provide a detailed description covering what the API does and how consumers should use it. At minimum include:

- Purpose and scope (in-scope vs out-of-scope).
- Intended audience and required licenses or entitlements (see [#specify-api-audience], [#document-required-licenses-for-api-collections]).
- Authentication model and high-level authorization expectations (see [#secure-endpoints-with-oauth-2-0], [#define-and-assign-scopes], [#define-user-capabilities-for-userauth-endpoints]).
- Primary workflows and "happy path" usage (link to guides/user manual; see [#provide-an-api-user-manual]).
- Major edge cases affecting client correctness: pagination defaults, filtering/sorting constraints, idempotency/retry guidance, consistency expectations.
- Versioning/deprecation model and how changes are communicated (see [#use-year-based-api-versioning-yyyy-revision], [#reflect-deprecation-in-openapi]).

Put this in OpenAPI `info.description` and/or tag-level descriptions, and link to deeper guides via `externalDocs`. A reviewer should be able to answer: what is this API for, who can use it, and how do I perform the primary workflows?

### describe-every-parameter-and-property
<RuleHeader
  id="describe-every-parameter-and-property"
  level="MUST"
  title="Describe Every Parameter and Property"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `properties:
  status:
    type: string
    enum: [ACTIVE, DISABLED]
    description: Current account state. Defaults to ACTIVE on creation.`,
    },
  ]}
/>

Every query parameter, path parameter, request property, and response property MUST have a clear description covering (as applicable):

- What the field means, not just its data type.
- Important constraints such as allowed values, ranges, patterns, and maximum lengths.
- Default or omission behavior when callers leave it out (see [#define-defaults-for-optional-properties], [#handle-null-values-correctly]).
- Security or privacy considerations when relevant.

Empty descriptions are not acceptable. Neither are descriptions that restate the property name (e.g., "The status.").

### keep-operation-summaries-to-5-words-or-fewer
<RuleHeader
  id="keep-operation-summaries-to-5-words-or-fewer"
  level="MUST"
  title="Keep Operation Summaries to 5 Words or Fewer"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}

    {

### avoid-qualifying-verbs
<RuleHeader
  id="avoid-qualifying-verbs"
  level="SHOULD"
  title="Avoid Qualifying Verbs"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "enabled": true,
  "active": true,
  "visible": false
}`,
    },
  ]}
/>

- Boolean fields and other descriptive properties SHOULD avoid qualifying verbs like `is`, `has`, `can` when the adjective alone is clear.
- Exception: use a verb when the adjective is genuinely ambiguous (e.g., `canDelete` may be clearer than `deletable`).

- ✅ `enabled` over `isEnabled`
- ✅ `active` over `isActive`
- ✅ `visible` over `isVisible`

### use-positive-semantics-for-boolean-fields
<RuleHeader
  id="use-positive-semantics-for-boolean-fields"
  level="SHOULD"
  title="Use Positive Semantics for Boolean Fields"
  externalDocs={[{ href: "https://cloud.google.com/apis/design/naming_convention", label: "Google API Naming Convention" }]}
  examples={[
    {
      lang: "json",

## Operation & Parameter Documentation

For most endpoints, the minimum documentation bar is:

- Explain what the operation does and who can use it.
- Describe every public parameter and property.
- Include realistic success and error examples.
- Reuse the standard `filters` and `sorters` wording where applicable.

### describe-the-filters-parameter-standard-format
<RuleHeader
  id="describe-the-filters-parameter-standard-format"
  level="MUST"
  title="Describe the Filters Parameter (Standard Format)"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?filters=status eq "ACTIVE" and createdAt gt "2025-01-01T00:00:00Z"`,
    },
  ]}
/>

When an endpoint supports `filters`, keep the parameter name, grammar, and description structure consistent across the API.

At minimum, document:

- the syntax,
- the supported fields,
- the supported operators,
- and at least one realistic example.

Use the template below as the default wording.

Organization OpenAPI linters (for example Spectral rule packs) that validate `filters` / `sorters` documentation MUST stay aligned with this template—operators, parameter names (`filters`, `sorters`), and the structure of the field list. If CI or a pack diverges from what authors see here, update the pack **or** this text in the same change set so teams are not caught between conflicting requirements.

```text
Filters results using the standard expression language.

Syntax:
  filters=<expr>

Operators:
  eq, ne, lt, lte, gt, gte, co (contains), sw (startsWith), ew (endsWith),
  in (set membership), pr (present)

Grouping:
  Use parentheses for grouping and AND/OR for boolean composition.

Supported fields:
  - fieldA (string)
  - fieldB (enum: ...)
  - created (date-time)

Examples:
  filters=status eq "ACTIVE"
  filters=(status eq "ACTIVE" or status eq "PENDING") and createdAt gt "2025-01-01T00:00:00Z"
```

- Each endpoint MUST document the supported field whitelist and include at least one filter example.

**Related**: shared query story in [#use-one-query-format-across-the-api] and implicit/default behavior guidance in [#document-implicit-filters-and-default-sorting].

### describe-the-sorters-parameter-standard-format
<RuleHeader
  id="describe-the-sorters-parameter-standard-format"
  level="MUST"
  title="Describe the Sorters Parameter (Standard Format)"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?sorters=status:asc,createdAt:desc`,
    },
  ]}
/>

When an endpoint supports `sorters`, keep the parameter name, grammar, and description structure consistent across the API.

At minimum, document:

- the syntax,
- the supported sort fields,
- the direction values,
- and the default ordering when `sorters` is omitted.

Use the template below as the default wording.

The same alignment requirement applies as for `filters` (see above): linter rules and this template MUST agree on syntax, allowed directions, and how defaults are described.

```text
Sorts results by one or more fields.

Syntax:
  sorters=<field>:<direction>[,<field>:<direction>...]

Direction:
  asc | desc

Supported fields:
  - name
  - createdAt
  - status

Default ordering:
  If sorters is omitted, results are ordered by <defaultSortPolicy>.

Examples:
  sorters=name:asc
  sorters=status:asc,created:desc
```

- Sort fields MUST be documented, and the API MUST guarantee a stable ordering for pagination.

**Related**: shared query story in [#use-one-query-format-across-the-api] and default ordering policy in [#document-implicit-filters-and-default-sorting].

      operationId: listAccounts
    post:
      operationId: createAccount
  /accounts/{accountId}:
    get:
      operationId: getAccount`,
    },
  ]}
/>

- Every operation MUST define a unique `operationId` in camelCase, unique across the entire spec (including across tags).
- These values are part of the public contract for tooling and SDKs. Do not rename `operationId` values without a compatibility plan.

#### Recommended patterns

- GET collection: `list<ResourcePlural>`
- GET item: `get<Resource>`
- POST collection: `create<Resource>`
- PUT/PATCH: `update<Resource>`
- DELETE: `delete<Resource>`
- POST search endpoints (see [#use-one-query-format-across-the-api]): `search<ResourcePlural>`
- Long-running jobs/resources: `create<Thing>Job` (POST), `get<Thing>Job` (GET), `list<Thing>Jobs` (GET)

| Method | Path | operationId |
| --- | --- | --- |
| GET | `/accounts` | `listAccounts` |
| GET | `/accounts/{id}` | `getAccount` |
| POST | `/accounts` | `createAccount` |
| POST | `/accounts/search` | `searchAccounts` |
| PATCH | `/accounts/{id}` | `updateAccount` |
| DELETE | `/accounts/{id}` | `deleteAccount` |

### provide-x-sailpoint-resource-operation-id-for-path-parameters
<RuleHeader
  id="provide-x-sailpoint-resource-operation-id-for-path-parameters"
  level="MUST"
  title="Provide x-sailpoint-resource-operation-id for Path Parameters"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `parameters:
  - name: accountId
    in: path
    required: true
    schema:
      type: string
    x-sailpoint-resource-operation-id: getAccount`,
    },
  ]}
/>

SailPoint tooling maps path parameters back to the operation that provides valid values for them.

- For path parameters (except enums and user-defined values), APIs MUST provide a camelCase operation identifier under `x-sailpoint-resource-operation-id` on the path parameter definition.
- The value MUST be camelCase and SHOULD align with the operation's `operationId` (see [#provide-a-camelcase-operationid-for-every-operation]).
- Do not change these identifiers without a compatibility plan — tooling depends on them.

```yaml
paths:
  /accounts/{accountId}:
    get:
      operationId: getAccount
      parameters:
        - name: accountId
          in: path
          required: true
          schema:
            type: string
          x-sailpoint-resource-operation-id: getAccount
```
