## Performance & Optimization
### support-fields
<RuleHeader
  id="support-fields"
  level="SHOULD"
  title="Support Partial Responses (fields)"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md#pagination", label: "Microsoft REST API Guidelines: Pagination" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts?fields=(id,name)&limit=50&offset=0`,
    },
  ]}
/>

- APIs SHOULD support a `fields` query parameter so clients can request only the fields they need.
- `fields` SHOULD apply to **collection GET endpoints** as well as single-resource GETs and dedicated `POST /.../search` endpoints. Do not limit field projection to search as a matter of convention.
- Field filtering MUST NOT apply by default — full responses remain the baseline.
- Document the allowed values and syntax explicitly (e.g., `fields=(id,name,status)`).
- If you support nested field selection, document the limits and behavior.
- Treat `fields` as part of the cache key for GET requests.

- ✅ `GET /accounts/{id}?fields=(id,name,status)`
- ✅ `GET /accounts?fields=(id,name)&limit=50&offset=0`
- ✅ `POST /accounts/search` with `fields` in the request body

### support-embedding
<RuleHeader
  id="support-embedding"
  level="SHOULD"
  title="Allow Optional Embedding"
  externalDocs={[{ href: "https://github.com/microsoft/api-guidelines/blob/vNext/Guidelines.md", label: "Microsoft REST API Guidelines" }]}
  examples={[
    {
      lang: "http",
      code: `GET /accounts/{id}?embed=(ownerRef,sourceRef)`,
    },
  ]}
/>

- APIs SHOULD support an `embed` query parameter to optionally include related sub-resources inline.
- Embedding MUST be opt-in (not the default) so baseline responses stay lean.
- Define an allowlist of embeddable relationships per endpoint.
- Limit embedding depth (depth = 1 is a good default).
- Document any performance considerations.

- ✅ `GET /accounts/{id}?embed=(ownerRef,sourceRef)`
- ✅ `GET /accounts?embed=(ownerRef)&limit=50&offset=0`
- ❌ Unlimited recursive embedding
- ❌ `embed=*` without documented limits

## API Operation & Monitoring
### meet-doc-quality
<RuleHeader
  id="meet-doc-quality"
  level="MUST"
  title="Publish an OpenAPI Specification (Meet Doc Quality Levels)"
  externalDocs={[{ href: "https://spec.openapis.org/oas/latest.html", label: "OpenAPI Specification" }]}
  examples={[
    {
      lang: "yaml",
      code: `paths:
  /accounts:
    get:
      summary: List accounts
      description: Returns a paginated list of accounts.
      operationId: listAccounts
      tags: [Accounts]
      security:
        - oauth2: [accounts:read]
      responses:
        "200": { $ref: "#/components/responses/AccountList" }
        "400": { $ref: "#/components/responses/Problem" }`,
    },
  ]}
/>

- All APIs MUST publish an OpenAPI specification accessible to intended consumers (public docs for public APIs, internal portal for internal-only).
- The published spec MUST be versioned and aligned with the documented API version (see [#use-calendar-versioning]).
- The spec SHOULD be the source for generated docs, SDKs, and contract validation where feasible.
- While [#require-openapi] requires that an OAS exists and is valid, this rule defines the quality bar.

#### Documentation quality levels

- **Level 0 (non-compliant)**: paths exist but missing schemas, responses, and security details.
- **Level 1 (minimum acceptable)**:
  - Every operation has `summary` + `description`.
  - Every operation defines success responses and expected error responses (see [#use-problem-details]).
  - Request/response schemas are defined (no `any`/untyped objects).
  - `security` is declared with required scopes (see [#use-oauth2], [#define-scopes]).
  - Every operation includes realistic success and error examples as required by [#require-examples].
- **Level 2 (required for external APIs; strongly recommended for internal)**:
  - Consistent tagging and `operationId` conventions.
  - Pagination/filtering/sorting parameters are documented where applicable, including supported field lists (see [#use-standard-query-params]).
  - Deprecations are marked with `deprecated: true` and migration guidance (see [#mark-deprecated]).
  - Changelog/revision info is maintained for contract changes (see [#use-calendar-versioning]).

Teams MUST have a checklist or review gate so new and changed endpoints meet the required level.

### return-request-ids
<RuleHeader
  id="return-request-ids"
  level="MUST"
  title="Return a Request ID on Every Response"
  externalDocs={[{ href: "https://www.w3.org/TR/trace-context/", label: "W3C Trace Context" }, { href: "https://opensource.zalando.com/restful-api-guidelines/#233", label: "Zalando: X-Flow-ID" }]}
  examples={[
    {
      lang: "http",
      code: `HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
X-Request-Id: 3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b`,
    },
  ]}
/>

- The server MUST generate a unique `X-Request-Id` header (UUID v4) on every response — including `4xx`, `5xx`, and `429`.
- Error response bodies MUST include the same value as `correlationId` (see [#use-problem-details]).
- If the client sends an `X-Request-Id` header, the server SHOULD echo it back (after validation) rather than generating a new one.
- For distributed tracing, services SHOULD support W3C Trace Context (`traceparent`/`tracestate` headers).

Error response (header matches body):

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
X-Request-Id: 3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b
```

```json
{
  "type": "https://developer.sailpoint.com/problems/validation-error",
  "title": "Validation error",
  "status": 400,
  "detail": "One or more fields are invalid.",
  "instance": "/accounts",
  "correlationId": "3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b"
}
```

Declare `X-Request-Id` as a shared response header component in OpenAPI:

```yaml
components:
  headers:
    X-Request-Id:
      description: Unique request identifier for tracing and support.
      schema:
        type: string
        format: uuid
```

**Related rules**: [#use-problem-details] correlationId, [#no-internal-errors] sanitized error responses.

### design-webhooks
<RuleHeader
  id="design-webhooks"
  level="SHOULD"
  title="Design Webhooks and Event Notifications"
  externalDocs={[{ href: "https://docs.stripe.com/webhooks", label: "Stripe: Webhooks" }, { href: "https://docs.github.com/en/webhooks", label: "GitHub: Webhooks" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "id": "evt-3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b",
  "type": "account.created",
  "timestamp": "2026-03-05T10:00:00Z",
  "tenantId": "tenant-abc",
  "data": {
    "id": "acct-123",
    "name": "Example Account",
    "status": "ACTIVE"
  }
}`,
    },
  ]}
/>

- APIs with meaningful state transitions SHOULD offer webhook notifications.
- Use one standard event envelope shape across the API.
- Every event MUST include `id`, `type`, `timestamp`, `data`, and `tenantId`.
- Document delivery guarantees explicitly. At-least-once delivery is recommended.
- Failed deliveries MUST be retried with exponential backoff, and docs MUST explain the retry behavior.
- Include an `X-Webhook-Signature` header with an HMAC-SHA256 signature and document how consumers verify it.
- The event `id` MUST be stable across retries so consumers can deduplicate.
- Provide a CRUD API for webhook subscriptions with filtering by event type.

```json
{
  "id": "evt-3f7c2b7f-1b4c-4f0e-9b8e-0b6a0a0b0a0b",
  "type": "account.created",
  "timestamp": "2026-03-05T10:00:00Z",
  "tenantId": "tenant-abc",
  "data": {
    "id": "acct-123",
    "name": "Example Account",
    "status": "ACTIVE"
  }
}
```

**Related rules**: [#require-https] HTTPS for webhook URLs, [#support-async-operations] webhooks complement async operations, [#return-request-ids] include X-Request-Id in webhook deliveries.

### provide-health-checks
<RuleHeader
  id="provide-health-checks"
  level="SHOULD"
  title="Provide Health Check Endpoints"
  externalDocs={[{ href: "https://datatracker.ietf.org/doc/html/draft-inadarei-api-health-check", label: "IETF Health Check Response Format" }, { href: "https://learn.microsoft.com/en-us/azure/architecture/patterns/health-endpoint-monitoring", label: "Azure: Health Endpoint Monitoring Pattern" }]}
  examples={[
    {
      lang: "json",
      code: `{
  "status": "UP",
  "checks": [
    { "name": "database", "status": "UP" },
    { "name": "cache", "status": "UP" },
    { "name": "search-index", "status": "DOWN", "detail": "Connection timeout" }
  ]
}`,
    },
  ]}
/>

- APIs SHOULD provide standardized health check endpoints for infrastructure probes and operational monitoring.

#### Standard endpoints

- `/health` or `/health/ready` — **Readiness**: returns `200` when all critical dependencies are reachable and initialized; returns `503` when alive but not ready.
- `/health/live` — **Liveness**: returns `200` if the process can respond. This check SHOULD be lightweight — no dependency checks, no database queries.

#### Response shape

```json
{
  "status": "UP",
  "checks": [
    { "name": "database", "status": "UP" },
    { "name": "cache", "status": "UP" },
    { "name": "search-index", "status": "DOWN", "detail": "Connection timeout" }
  ]
}
```

- Use `"UP"`, `"DOWN"`, or `"DEGRADED"` for status values.
- The `checks` array is optional for liveness but recommended for readiness.
- Include `detail` only when it helps operators diagnose issues — never expose connection strings, credentials, or internal hostnames.

#### Authentication

- Health endpoints SHOULD NOT require authentication — load balancers and Kubernetes probes typically cannot present tokens.
- If your security policy requires authentication on all endpoints, provide an exemption for health checks or use a separate internal port.

#### Operational guidance

- Keep liveness checks fast (< 100ms) — slow liveness checks cause unnecessary restarts.
- Readiness checks MAY be slower but SHOULD complete within a few seconds.
- Do not include health endpoints in your public OpenAPI spec — document them in operational runbooks instead.
- Return `Cache-Control: no-store` on health responses to prevent stale caching.

**Related rules**: [#use-standard-status-codes] status codes (503 for not-ready), [#no-internal-errors] never expose internal details.
